### C1. [HIGH / ui-thread-block] Installer pause gate can deadlock the UI thread permanently when Cancel modal is open as the copy step finishes

**Location:** `src/ProoveGaming.Installer/Views/MainWindow.Installation.cs:92`  |  **Panel votes:** 3/3 real

**Evidence:** RunInstallAsync runs on the Avalonia UI thread (it sets control state directly, e.g. GetStatusText().Text at lines 80/83/88, and is reached from the async void OnNextClick handler). At lines 52, 92 and 107 it calls WaitIfInstallPausedOrCancelled, which does a blocking `_installPauseGate?.Wait(cancellationToken)` (line 181) on a ManualResetEventSlim. The gate is Reset by OpenCancelModal (MainWindow.Modal.cs:23) and Set only by CloseCancelModal (MainWindow.Modal.cs:46) — both UI-thread click handlers. CopyDirectoryAsync's Task.Run worker checks the gate per file (line 751) BEFORE each copy, so if the user opens the Cancel modal after the worker has passed the last file's gate check, the copy Task completes, the await at line 90 resumes on the UI thread, and line 92 blocks the UI thread on a gate that only a UI-thread click can open. The CancellationToken cannot save it either: it is cancelled only by the modal's confirm button, which also needs the frozen UI thread. Unrecoverable — the installer window is dead and must be killed.

**Trigger scenario:** During a real (Release) install, the user clicks Cancel while the last file of the payload — typically the multi-hundred-MB self-contained app exe, taking seconds — is being copied, and the confirmation modal is still open when the copy completes. The whole installer window freezes permanently: the modal's Yes/No buttons never respond and the process must be terminated from Task Manager.

**Impact assessment (adversarial panel):** Mechanism confirmed line-by-line: RunInstallAsync resumes on the Avalonia UI thread (awaited from async void OnNextClick, MainWindow.axaml.cs:106; sets controls directly; no ConfigureAwait(false)), and Installation.cs:92 -> line 181 does a timeout-free ManualResetEventSlim.Wait on that thread. The only ways out — CloseCancelModal.Set() (Modal.cs:46) and ConfirmCancelModal's token Cancel (Modal.cs:60) — are button-click ICommand handlers needing the same frozen UI thread; no timer or external cancel exists, so the deadlock is permanent. Quantified impact: the fatal window is the copy duration of the LAST enumerated payload file (worker gate-checks per file at line 751 on a background thread, so earlier modal opens park it safely) — roughly tens of ms to ~3 s if a large binary enumerates last, out of a ~5-15 s copy phase, i.e. maybe 1-25% of cancel-during-copy clicks, and cancel during the visible 'Copying files' phase is ordinary behavior for a one-shot installer. Not per-keystroke frequency, but when it fires the outcome is total: window permanently dead (must kill via Task Manager), the finally block (lines 161-175) never runs so the multi-hundred-MB staging dir leaks in %TEMP%, rollback never runs leaving a half-written install dir, and the DeviceHost service — stopped at line 84 before the copy — is left down on a re-install. That is material harm, not negligible. Severity calibration: 'high' is defensible under 'freezes UI in normal use', though borderline medium given the intermittent race window and that the user can kill and re-run the installer; the unrecoverable-in-app consequences (no rollback, stopped service) keep it real regardless of the high/medium label.

### C3. [MEDIUM / ui-thread-block] SettingsRepository async facade runs synchronous SQLite writes inline on the UI thread

**Location:** `src/ProoveGaming.App/Services/SettingsRepository.cs:126`  |  **Panel votes:** 3/3 real

**Evidence:** Every Save*/Load*Async method does its LocalStorageService work synchronously before returning Task.CompletedTask / Task.FromResult — e.g. SaveDpiPresetsAsync (lines 124-130) issues 4 `_storage.SetDeviceSetting(...)` calls PER DPI stage, and each SetDeviceSetting (LocalStorageService.cs:813-834) takes the global SemaphoreSlim via AcquireLock() (`_lock.Wait()`, LocalStorageService.cs:42) and executes an auto-committed INSERT (one journal fsync per statement — the connection never enables WAL; only `PRAGMA foreign_keys` is set in the ctor at LocalStorageService.cs:56-60). Callers fire-and-forget these from UI property setters, e.g. DeviceDetailsViewModel.cs:665 `_ = _settings.SaveActiveDpiStageAsync(...)` and DeviceDetailsViewModel.cs:679 `_ = _settings.SaveMouseSettingsAsync(...)` — the `_ =` offloads nothing because the write completes synchronously on the calling (UI) thread.

**Trigger scenario:** User drags the DPI slider or changes polling rate / mouse settings in device details: each change performs one or more locked, individually-fsynced SQLite commits on the Avalonia dispatcher thread. With several DPI stages that is 4×N sequential disk commits per save; on a slow HDD or when a background Task.Run reader (e.g. DeviceDetailsViewModel.Buttons.cs:138 GetMacros) holds the lock, the UI stalls for the duration.

**Impact assessment (adversarial panel):** Mechanism verified: SettingsRepository (SettingsRepository.cs:124-130 etc.) completes all "async" saves synchronously on the caller; SetDeviceSetting (LocalStorageService.cs:813-834) does _lock.Wait() plus one auto-committed upsert per call, no WAL (ctor lines 48-62 sets only foreign_keys), so ~2 fsyncs per commit on the UI thread. However the finding's headline frequency is overstated: mouse-slider and app-preference saves are debounced 300 ms (DeviceDetailsViewModel.Settings.cs:124-128, 443-446), DPI stage / polling-rate changes are discrete clicks writing 1 commit each, and the 4-commits-per-stage SaveDpiPresetsAsync path has exactly one caller — the restore-defaults button (Settings.cs:225), gated per click. Quantified impact: common path = 1-2 commits ≈ 2-10 ms on idle SSD (imperceptible), ~50-200 ms on HDD; worst path = restore-defaults with 4N+2 ≈ 18-34 sequential fsynced commits inline on the dispatcher ≈ 50-150 ms on idle SSD, ~1-2 s on HDD or on any disk under write load. Lock-contention amplifiers are bounded: background GetMacros is one short SELECT; MigrateGuestToUserAsync holds the semaphore across awaits but only for local SQLite in one transaction, once per login. No unbounded growth. Verdict: real, because the block recurs on every settings interaction, its tail latency is disk-controlled (fsync on the UI thread) rather than app-bounded, and the restore-button burst is a reproducible visible hitch (seconds on HDD/loaded disk) — material under this repo's explicit "any visible hitch is a bug" standard. Severity stays medium, not high: click-gated, debounced elsewhere, fully recoverable, and sub-perception on the modal idle-SSD machine. Confidence medium only because the material-impact case depends on disk conditions (HDD or I/O pressure), not the modal configuration.

### C4. [MEDIUM / ui-thread-block] Preset save/switch runs multi-table SQLite transactions synchronously on the UI thread under the global storage lock

**Location:** `src/ProoveGaming.App/Services/LocalStorageService.cs:42`  |  **Panel votes:** 2/3 real

**Evidence:** Every public LocalStorageService method funnels through AcquireLock() → `_lock.Wait()` (line 42) — a synchronous SemaphoreSlim wait — then runs blocking SQLite I/O. The heavy call sites execute directly in UI RelayCommands/handlers: ConfirmSavePreset (DeviceDetailsViewModel.Presets.cs:307, a [RelayCommand]) calls `_localStorage.SavePresetSnapshot(...)` at Presets.cs:323 (7-table wipe+copy transaction, LocalStorageService.cs:1975+); the preset-apply path calls `_localStorage.LoadPresetSnapshotToDevice(...)` at Presets.cs:541 (7 DELETEs + 7 INSERT..SELECTs + Commit, LocalStorageService.cs:1817-1968). Because the lock is global, any of these UI-thread calls also blocks behind concurrent background readers (Task.Run reads at DeviceDetailsViewModel.Presets.cs:205, .Rgb.cs:873, .Buttons.cs:138) before doing its own I/O.
[corroborated by second finder] Every sync LocalStorageService method funnels through AcquireLock() → `_lock.Wait()` (line 42) with no timeout, then executes SQLite commands synchronously on the caller's thread. The class comment (lines 24-28) states the UI thread is a caller by design. Concrete UI-thread call site: ConfirmSavePreset is a [RelayCommand] (DeviceDetailsViewModel.Presets.cs:307) that calls _localStorage.SavePresetSnapshot at line 323 — a multi-table DELETE + INSERT transaction with a commit fsync (LocalStorageService.cs:1975-1998 onward) — plus SetAppliedPreset at line 335, all on the click. **Trigger scenario:** User clicks SAVE in the Save Preset dialog or switches presets while a background storage read (device reconnect → GetRgbState, or the preset dirty-check PresetMatchesLiveState) holds the lock: the dispatcher thread parks in _lock.Wait(), then executes a multi-statement transaction plus commit fsync — a visible hitch on every preset operation, worse on slow disks.

**Impact assessment (adversarial panel):** Mechanism verified as described: AcquireLock() at LocalStorageService.cs:42 is a sync SemaphoreSlim.Wait with no timeout, ConfirmSavePreset (Presets.cs:306-337) runs SavePresetSnapshot/SetAppliedPreset synchronously on the dispatcher, LoadPresetSnapshotToDevice (1817-1968) likewise on preset switch, and no WAL pragma exists so commits fsync in DELETE-journal mode. But quantified impact is minor: the transactions move low hundreds of rows of per-device config (key_bindings ~130 rows max, actuation ~100 slots, rest single/double digits), so cost is fsync-dominated — ~10-50 ms on SSD, bounded worst case ~100-300 ms on HDD/AV-scanned disk. Lock contention adds single-digit ms (background readers run tiny local SELECTs; the longest holder, MigrateGuestToUserAsync, awaits only local SQLite and fires once per sign-in). Trigger frequency is explicit user clicks (preset save/switch) or device replug/card add/delete — a few per session, never per-keystroke or per-frame; the per-change saves are debounced. A bounded, click-scoped, few-times-per-session stall at or below normal click-response latency, with no unbounded growth and no hang path (everything under the lock is local SQLite on one serialized connection), is negligible for a desktop app; the claimed medium 'visible hitch on every preset operation' only holds on slow spinning disks and even there is a one-off sluggish click, not a freeze. Confidence medium rather than high because I could not measure real disk timings and low-end HDD machines could occasionally reach a perceptible ~200 ms click.

### C5. [MEDIUM / sync-over-async] Guest-to-user migration transaction executes entirely on the UI thread despite its async signature

**Location:** `src/ProoveGaming.App/Services/LocalStorageService.cs:2960`  |  **Panel votes:** 2/3 real

**Evidence:** MigrateGuestToUserAsync (LocalStorageService.cs:2960-3139) rekeys 13 tables (9 ReKeyAsync wipe+rekey pairs plus macros/presets/notifications/devices) inside one transaction using Microsoft.Data.Sqlite's async APIs (`BeginTransactionAsync`, `ExecuteNonQueryAsync`). Microsoft.Data.Sqlite executes its async methods synchronously (the provider does not support async I/O), so nothing ever yields: the whole transaction, including the commit fsync at line 3136, runs on whatever thread awaits it. It is awaited from the UI thread at MainWindow.axaml.cs:447 (`await _localStorage.MigrateGuestToUserAsync(guestSessionId, customerId);` inside the registration/sign-in flow), immediately followed by the synchronous `_localStorage.ClearSession()` at MainWindow.axaml.cs:453 — with no Task.Run offload, unlike the storage reads elsewhere in the codebase.

**Trigger scenario:** A guest with a populated database (macros with events, per-key actuation rows, RGB effects, presets across several devices) signs in or registers: the dispatcher thread runs the full 13-table rekey transaction plus commit synchronously, freezing the sign-in UI for the duration; the app cannot show progress because the freeze is on the thread that would paint it.

**Impact assessment (adversarial panel):** Mechanism is accurate (Microsoft.Data.Sqlite completes async APIs synchronously; the transaction at LocalStorageService.cs:2960-3139 runs on the UI thread when awaited from MainWindow.axaml.cs:447), but the impact is negligible. Trigger: exactly once per account lifetime — the guest→user upgrade at registration, gated at MainWindow.axaml.cs:445 and immediately followed by EndSession/ClearSession that consume the guest id, so it can never re-fire. Volume: all ~24 statements are scoped to one guest's rows across 13 small tables (per-key bindings ~100 rows/keyboard, actuation ~100, a few macros/presets/effects); macro_events, the only potentially large table, is deliberately untouched (lines 3080-3082). Duration: hundreds-to-low-thousands of row updates plus one rollback-journal commit (no WAL pragma; constructor sets only foreign_keys=ON) = ~10-50 ms typical on SSD, ~100-300 ms absolute worst case on HDD with unusually large history. The lock wait at line 2967 is a true async WaitAsync, so contention yields rather than blocks. The stall lands mid-screen-transition right after two awaited network calls that each take longer, with no typing or animation in flight. A sub-frame-budget-to-sub-second, strictly one-time dispatcher stall during a page transition is imperceptible in practice — a legitimate style/hygiene violation of the repo's no-sync-I/O rule, but not a material freeze for a desktop app.

### C6. [MEDIUM / sync-over-async] Synchronous SQLite storage calls run on the UI thread behind a shared SemaphoreSlim.Wait()

**Location:** `src/ProoveGaming.App/Services/LocalStorageService.cs:42`  |  **Panel votes:** 2/3 real

**Evidence:** AcquireLock() does a blocking _lock.Wait() (line 42) on a SemaphoreSlim whose own comment (lines 24-28) states it is also taken by background threads ('the App reads from a background thread (device reconnect -> GetRgbState) while the UI thread writes'). The synchronous storage API is called directly on the Avalonia dispatcher thread from the app shell: App.axaml.cs lines 66/82/85/99 (GetSavedAuth, GetSessionState, ClearData, GetDevices at startup) and line 116 (Flush inside the desktop.Exit handler), and MainWindow.axaml.cs line 86 (GetLockoutUntil), 315 (InitializeSession), 332 (ClearData), 352 (ClearSession), 466 (SaveAuth). Each such call is blocking file I/O (SQLite) on the UI thread, and if a background reader holds _lock at that moment the dispatcher additionally blocks in _lock.Wait() for the full duration of the background query — the repo rule forbids exactly this pattern (sync waits/blocking I/O on the dispatcher).

**Trigger scenario:** User signs in or logs out (SaveAuth/ClearSession/ClearSavedAuth on the UI thread) at the same moment a reconnecting device's background thread is inside a storage read holding _lock — the UI freezes until both the background query and the UI-thread SQLite write complete. On a slow/contended disk (or a long device-restore read) this is a visible input hitch; it recovers on its own.

**Impact assessment (adversarial panel):** Mechanism confirmed (LocalStorageService.cs:39-43 blocking Wait; sync SQLite on dispatcher at App.axaml.cs:66-116, MainWindow call sites), but quantified impact is negligible. (1) Duration: background lock holders are 1-2 PK-indexed SELECTs on a tiny local SQLite DB (<1 MB; per-device settings rows) — ~0.1-5 ms hold time. The only long holder is MigrateGuestToUserAsync (lines 2960+), one local transaction over ~12 small tables, all awaits local SQLite (no network/device I/O under the lock): tens of ms typical, ~100-300 ms worst case on slow disk, and it runs once per sign-in. (2) Frequency: the App.axaml.cs startup calls (GetSavedAuth/GetSessionState/GetDevices) run once per launch BEFORE MainWindow is constructed (line 120) and before any background reconnect readers exist — pure startup latency, not a visible hitch; Flush runs once inside desktop.Exit where a blocked dispatcher is invisible. MainWindow calls fire only on explicit sign-in/sign-out, a handful per run, each a single-row query. Background contention (DeviceDetailsViewModel.Rgb.cs:873 Task.Run GetRgbState) fires per device reconnect, not per keystroke. (3) Bound: collision requires a user auth action inside a ~1-5 ms background lock window; worst realistic outcome is one sub-second hitch during the sign-in flow (UI-thread SaveAuth racing the migration transaction), fully self-recovering, no growth, no leak. A rule violation worth cleaning up, but actual user-visible impact in normal use is essentially zero, so the 'medium' severity is not supported; this is low at most.

### C7. [MEDIUM / resource-leak] Mouse RGB service caches never evicted — replugged mouse served a dead DevicePath until DeviceHost restart

**Location:** `src/ProoveGaming.Infrastructure/Services/DeviceRgbServiceFactory.cs:22`  |  **Panel votes:** 2/3 real

**Evidence:** `private readonly ConcurrentDictionary<(int, int, string), EasenMouseService> _serviceCache = new();` (line 22) and `_telinkCache` (line 25) are populated in CreateEasenMouseService (line 234 `_serviceCache[key] = service;`) and CreateTelinkMouseService (line 284) and are never removed from. The factory's own comment (lines 18-21) states: "KNOWN PRE-EXISTING DEFECT ... neither this cache nor _telinkCache is ever invalidated, so a cached mouse service keeps its stale DevicePath after a replug into a different USB port until DeviceHost restarts." The keyboard cache (_keyboardCache, line 38) got the fix — it is cleared in OnDeviceListChanged (line 62) — but the two mouse caches were left out of that handler. Each cached EasenMouseService/TelinkMouseService pins the HidSharp HidDevice for the old interface path; every later TryOpen on it fails, so RGB/DPI/button/macro writes for that unit silently return false forever. Entries also accumulate one per (VID,PID,ContainerId) ever seen, so dead entries are retained for the process lifetime (bounded by distinct units, so growth is modest — the stale-handle behaviour is the real cost).

**Trigger scenario:** User unplugs their BLAZE or TAIPAN mouse and plugs it into a different USB port (or through a hub) while DeviceHost is running. DpiStageMonitor and the gRPC DeviceService both hit the stale cache entry (DeviceService.cs line 166/195 CreateForDevice), TryOpen fails on the dead path, and every RGB/DPI/preset apply no-ops until the ProoveGamingDeviceHost service is restarted.

**Impact assessment (adversarial panel):** Mechanism confirmed in DeviceRgbServiceFactory.cs: _serviceCache (line 22) and _telinkCache (line 25) are populated (lines 234, 284) and never invalidated — OnDeviceListChanged (lines 60-63) clears only _keyboardCache; the defect is even self-documented at lines 18-21. EasenMouseService retries TryOpen on the construction-time HidDevice (lines 206, 278) and never re-resolves the path, so a stale entry never self-heals. Quantified impact: as a LEAK it is negligible — cache key is (VID, PID, ContainerId), ContainerId is port-independent, so entries are bounded at one per distinct physical mouse ever seen (typically 1-3), each ~1-5 KB; total stale retention <~20 KB. The material cost is FUNCTIONAL: after one different-port replug (near-daily for laptop dock/undock users, rare for fixed desktops), the same cache key serves the instance bound to the dead location-specific DevicePath, so every mouse write — RGB, DPI, presets, button remap, macros via DeviceService.cs lines 166-367 and DpiStageMonitor/TaipanStateMonitor — silently returns failure for that unit until the ProoveGamingDeviceHost service restarts. With Windows fast startup, shutdown+start does not restart services, so the broken window can last days to weeks, and ordinary users have no recovery action. A single common physical action permanently disabling the 24/7 service's core function for a device is material; medium (bounded, no UI freeze, recoverable only via service restart) is the correct severity.

### C8. [MEDIUM / other] Keyboard/T800 RGB services await DeviceGate with no CancellationToken and no timeout — un-cancellable pile-up behind a long or wedged gate holder

**Location:** `src/ProoveGaming.Infrastructure/Services/AressKeyboardRgbService.cs:54`  |  **Panel votes:** 2/3 real

**Evidence:** AressKeyboardRgbService.cs:54, CyrexKeyboardRgbService.cs:52, RampageKeyboardRgbService.cs:70 and T800KeyboardRgbService.cs:128 all do `using var gate = await DeviceGate.AcquireAsync(_device.DevicePath);` — no CancellationToken and no timeout. DeviceGate.AcquireAsync (DeviceGate.cs:71-76) waits on the per-path SemaphoreSlim indefinitely when the default token is passed. The same interface is held for seconds at a time by the key-mapping/macro services (T800KeyboardMacroService.cs:74 takes the gate around a ~100-packet write with 20 ms Thread.Sleep pacing per packet, line 204; RampageKeyboardKeyMappingService takes it at line 135 around 4 retry attempts of a full 384-byte read-modify-write-verify). The codebase itself documents the wedged-holder failure mode: TelinkMouseService.cs:41-45 ("a driver call wedged inside the gate — would turn every subsequent config write into a permanent hang with no way out but restarting the service") and defends with a 10 s GateTimeout (lines 45, 219-232). None of the four RGB services has that defence, and because no token is flowed, a gRPC deadline expiring on the App side does not dequeue the waiter — each retried user action adds another permanently queued waiter task on the semaphore.

**Trigger scenario:** A macro-library sync or key-matrix write is in flight over the 2.4G receiver (multi-second gate hold) while the user drags the RGB colour slider: every slider-driven SetLed gRPC call queues an un-cancellable waiter and then executes serially after the transfer. If the gate holder ever wedges in a driver call (the failure TelinkMouseService documents as observed), all subsequent RGB writes for that keyboard hang forever and waiter tasks accumulate until DeviceHost restarts.

**Impact assessment (adversarial panel):** Mechanism verified (no token/timeout at AressKeyboardRgbService.cs:54, CyrexKeyboardRgbService.cs:52, RampageKeyboardRgbService.cs:70, T800KeyboardRgbService.cs:128; DeviceService.cs:178 drops context.CancellationToken; App LED call has no deadline), but quantified impact is negligible. (1) Producer rate is human-bounded: LED writes fire once per settled slider edit via a 300 ms trailing debounce (DeviceDetailsViewModel.Rgb.cs:356-370), and the animation timers are UI-glow-only — no automated caller exists. (2) Normal-use pile-up behind the worst-case ~5-15 s T800 macro upload (16 slots x 20 ms/packet x up to 3 attempts) is at most a few dozen waiters at ~1-5 KB each (semaphore node + state machine + gRPC call context) = tens of KB, draining at ~30-65 ms per RGB write — bounded, recoverable, no UI freeze. (3) The competing long holders are deadline-bounded: macro/key-mapping gRPC calls carry 20-60 s deadlines whose tokens ARE flowed into their gate acquires and inter-packet checks (DeviceService.cs:340,520), so the gate frees within a minute except for a kernel call wedged mid-DeviceIoControl. (4) That wedge is hypothetical — TelinkMouseService.cs:41-45 is defensive phrasing ('would turn'), not an observed failure — and if it happened, RGB is dead until DeviceHost restart with or without the token: cancellation would only make waiters fail fast, not restore the feature. Incremental accumulation is bounded by human retry patience (~10-30 waiters, <100 KB). Worth a low-severity hardening fix (Telink-style GateTimeout), but not material for a desktop app or 24/7 service; confidence medium only because real-world wedge frequency is unknowable from code.

## 4. Completeness critic (what the audit itself may have missed)

SUBSTANTIATED MISSES (spot-checked by reading code)

1. App-side gRPC stream lifecycle has zero findings, and there is a real one. src/ProoveGaming.App/Services/UsbHidDeviceService.cs, AwaitServerStreaming (lines 707-759): the read loop runs in a swallowed-exception Task.Run (724-734), while the outer method sits in a `while (!cancellationToken.IsCancellationRequested) Task.Delay(3000)` keep-alive loop (736-746). If the DeviceHost dies or the stream ends mid-session, readTask completes silently but nothing cancels the token — the token is cancelled only by StopCommunication or the *next* RestartCommunication, which never runs because StartCommunication (634-642) is still awaiting this very task via Task.WhenAny (673). Result: after a DeviceHost restart, live device events (connect/disconnect, DPI, battery) are permanently dead until App restart, with no reconnect despite the reconnect loop existing. Medium (recoverable by restart, silent in normal service-update scenario).

2. Notification growth is uncapped. HomeViewModel.AddNotification/InsertNotification (372-422) inserts into Notifications, NotificationGroups, and SQLite with no cap or age pruning visible in the add path. Worth one targeted look at whether any prune exists elsewhere.

Serilog in DeviceHost (appsettings.json lines 18-26): daily rolling file to %TEMP%/Logs with no explicit retainedFileCountLimit/fileSizeLimitBytes — bounded only by Serilog defaults (31 files x 1 GB).
