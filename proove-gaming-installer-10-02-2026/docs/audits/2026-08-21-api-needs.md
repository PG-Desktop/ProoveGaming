## 1. [HIGH] Cloud settings sync — /api/settings push/pull for the full per-owner device-settings graph (presets, macros, key/button bindings, RGB, DPI/tuning, actuation, app preferences)

**Files:** src/ProoveGaming.App/Services/ISettingsSyncService.cs, src/ProoveGaming.App/Services/SettingsSyncService.cs, src/ProoveGaming.App/Services/LocalStorageService.cs, src/ProoveGaming.App/Services/SettingsRepository.cs, src/ProoveGaming.App/Views/MainWindow.axaml.cs, src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.Presets.cs, src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.KeyAssignments.cs, src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.Rgb.cs

**Current state:** Explicitly stubbed client seam, verified by re-read: SettingsSyncService.OnGuestUpgradedAsync (lines 16-22) only logs 'Settings sync stub: guest -> customer {CustomerId}. Server API not yet available.' and returns Task.CompletedTask; ISettingsSyncService's comment states there is no /api/settings endpoint yet. It is called from MainWindow.axaml.cs right after LocalStorageService.MigrateGuestToUserAsync rekeys every guest-owned SQLite row to the customer id — locally only. The entire settings graph is owner-scoped local SQLite: presets + snapshot children (preset_rgb, preset_settings, preset_button_bindings, preset_key_bindings, preset_key_macro_bindings, preset_actuation, device_applied_preset), macros + macro_events (per LocalStorageService comments the App is sole source of truth — device flash holds only anonymous event lists, so names/repeat modes/bindings are unrecoverable from hardware), button_bindings / key_bindings / key_macro_bindings (App-truth; DeviceHost no longer persists bindings), device_rgb / device_rgb_effect, device_settings (DPI stages, polling rate, debounce, lift-off, volumes), and device_actuation. Nothing ever leaves the machine.

**API need:** Authenticated /api/settings (or equivalent) endpoint set keyed by customer id + device type (vid/pid/device_key): (1) push the migrated settings bundle at guest→customer upgrade — the exact call OnGuestUpgradedAsync is the seam for; (2) push incremental changes for a signed-in user; (3) pull on sign-in from a fresh machine. Payload must cover presets with snapshots, macros with ordered events (synced atomically with presets since snapshots reference macro_id), key/button/macro bindings, RGB state, DPI/tuning, actuation, and app preferences. Exclude saved_auth/tokens from any sync payload.

**Rationale:** Merged from three analysts' overlapping items (sync seam, presets, macros, bindings, RGB, tuning) — all ride the same endpoint, so one API need. The client deliberately reserved and stubbed this integration point, the schema is already owner-scoped in sync-ready shape, and accounts already exist server-side — yet a reinstall or second PC loses every macro, preset and remap despite the user being signed in. Macros and presets are the sharpest edge: hand-recorded content the hardware cannot give back. This is account-data loss risk, the definition of high.

## 2. [HIGH] Contact Us — shipped UI silently discards messages; backend api/contact_us route missing

**Files:** src/ProoveGaming.App/ViewModels/HomeViewModel.cs, src/ProoveGaming.App/Services/AuthApiService.cs, src/ProoveGaming.App/Services/IAuthApiService.cs

**Current state:** Verified by re-read: HomeViewModel.SendContactUsAsync (lines 274-319) validates the form, plays a fixed 2 s pixel-loader animation via Task.Delay, then shows an acceptance toast and bell entry — no API call anywhere. The comment at lines 279-285 states 'No backend yet (QA 2026-08-21) ... no API call ... until the api/contact_us route exists' and that toast wording deliberately claims acceptance, not delivery. AuthApiService.ContactUsAsync is fully implemented as the ready client contract (POST api/contact_us, optional Bearer token) with zero callers.

**API need:** Stand up the backend api/contact_us route matching the already-coded client contract, then wire SendContactUsAsync to IAuthApiService.ContactUsAsync (awaiting the real request instead of the spinner delay, flowing a CancellationToken per the file's own TODO) and restore 'sent' wording.

**Rationale:** A shipped, visible flow accepts user support messages and drops them on the floor while showing success-adjacent feedback. Client work is essentially done — the entire gap is the missing server route. Smallest effort-to-impact ratio of any high item.

## 3. [HIGH] Firmware update service — Firmware section ships with hardcoded fake version and no-op button

**Files:** src/ProoveGaming.App/Views/DeviceDetails/Sections/FirmwareSectionView.axaml, src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.Firmware.cs, src/ProoveGaming.App/Views/SingleCard.axaml, src/ProoveGaming.GrpcDependencies/Protos/deviceservice.proto

**Current state:** Verified by re-read: DeviceDetailsViewModel.Firmware.cs is a single empty handler — `private void CheckFirmwareUpdates() { }` (line 8) behind the shipped CHECK FOR UPDATES button. FirmwareSectionView.axaml shows literal placeholder text 'Current Version: v1.2.3' and 'Device firmware is up to date and running the latest stable version.' to every user for every device. SingleCard.axaml carries a hidden firmware-update text block. deviceservice.proto has no RPC to read the device's real firmware version, and no DFU RPC — though vendor probes (X43Mouse.cs opcode 0x80) show the firmwares expose version reads, so the device side is feasible.

**API need:** Firmware update backend: endpoint keyed by vid/pid + current firmware revision returning latest-version metadata, release notes, and a signed firmware binary download. Requires a companion DeviceHost gRPC RPC to read the real firmware version from hardware. Consumed by the existing Firmware section UI.

**Rationale:** Shipped-but-broken per the priority definition: the UI unconditionally lies (every device is 'v1.2.3' and 'up to date') and its action button does nothing. Firmware delivery is also table stakes for a peripheral suite (Synapse, G Hub, GG all ship it) and is the only channel for fixing device-side bugs in the field.

## 4. [HIGH] App self-update — no version-check endpoint; installed base frozen at install time

**Files:** src/ProoveGaming.App/App.axaml.cs, src/ProoveGaming.App/appsettings.json, src/ProoveGaming.Installer/Views/MainWindow.Installation.cs, .github/workflows/release.yml

**Current state:** No version-check or self-update code exists in App or Installer (grep finds only UI-update methods and localization strings). appsettings.json declares exactly two remote endpoints: DeviceHost gRPC on localhost:5000 and UsersApiBaseUrl for auth. Distribution is a manually-triggered GitHub Actions workflow attaching a zipped installer to a date-tagged pre-release; nothing on a user's machine ever learns a newer build exists.

**API need:** App-update endpoint: GET latest version + installer download URL + release notes (a static versions.json behind the site suffices), polled at startup / periodically by the tray-resident App to prompt 'new version available'; optionally consumed by the installer too.

**Rationale:** A tray-resident app installed from a pre-release zip has no path to ship fixes to its installed base — including field-class bugs like the DeviceHost 23 GB memory leak already hit in this codebase. Every other item on this list that requires a client change is gated on users being reachable with updates at all.

## 5. [MEDIUM] Session token lifecycle — no refresh/validate endpoint; expiry approximated client-side and discovered reactively

**Files:** src/ProoveGaming.App/Views/MainWindow.axaml.cs, src/ProoveGaming.App/ViewModels/WelcomeViewModel.cs, src/ProoveGaming.App/Services/ApiResponse.cs, src/ProoveGaming.App/ViewModels/ProfileViewModel.cs

**Current state:** Login stores SessionTokenExpiresAt = DateTime.UtcNow.AddDays(TokenExpiresInDays ?? 30) (MainWindow.axaml.cs line 431, WelcomeViewModel.cs line 246). IAuthApiService has no refresh, validate, or keep-alive endpoint; expiry surfaces only when a protected call answers INVALID_OR_EXPIRED_TOKEN / TOKEN_REQUIRED, which ProfileViewModel special-cases at five separate sites (lines 159, 229, 437, 644-645, 784, 957-958). Web-side password change wipes all tokens (v1.7 §11 per line 225), amplifying mid-session invalidation.

**API need:** Token refresh (or session-validate/keep-alive) endpoint so long-lived tray sessions — the app sits in the tray for days per AppResilience comments — survive past the token window without full re-login.

**Rationale:** Common scenario, recoverable by re-login: the session degrades every protected feature at once when the token silently expires, and the five duplicated expiry-handling sites are the visible client cost of the missing endpoint. Becomes more important once settings sync (item 1) makes protected calls routine.

## 6. [MEDIUM] In-app password management — reset_password client endpoint is dead code, and no authenticated change-password endpoint exists

**Files:** src/ProoveGaming.App/Services/AuthApiService.cs, src/ProoveGaming.App/Services/IAuthApiService.cs, src/ProoveGaming.App/ViewModels/WelcomeViewModel.cs, src/ProoveGaming.App/ViewModels/ProfileViewModel.cs

**Current state:** Verified by grep: ResetPasswordAsync (POST api/reset_password, code + new_password) exists only in IAuthApiService.cs:14 and AuthApiService.cs:46 — zero callers. Both reset entry points (WelcomeViewModel.SendPasswordResetAsync line 386, ProfileViewModel.SendChangePasswordResetAsync line 860) call only ForgottenPasswordAsync and stop at 'link sent'; ProfileViewModel lines 803-806 document the password is actually changed on the website via the emailed link, and that api/profile/password_link is no longer called by the launcher. The Profile 'Change password' dialog takes no current/new password — it just triggers the email.

**API need:** Two coupled decisions: (1) an authenticated change-password endpoint (Bearer token, current + new password) so the Profile Security dialog can complete in-app; (2) either build the in-app code-entry + new-password step that consumes the already-coded api/reset_password, or delete ResetPasswordAsync as dead surface.

**Rationale:** Merged two analyst items about the same broken flow. Users are bounced from the app to email + website for a routine security action; meanwhile the client carries an unreferenced API method masquerading as capability. Functional today via the website detour, hence medium not high.

## 7. [MEDIUM] Email change — no verification/confirm endpoint; typo'd address becomes the login identity

**Files:** src/ProoveGaming.App/ViewModels/ProfileViewModel.cs

**Current state:** ConfirmEditEmail (lines 713-759) sends the new address straight through POST api/profile/update; the comment at lines 692-694 states 'v1.7 has no email-verification endpoint: api/profile/update takes the new address directly and answers with INVALID_EMAIL / EMAIL_ALREADY_EXISTS'. The only client-side safeguard is a format regex.

**API need:** Email-verification / confirm-new-address endpoint (send code or link to the new mailbox, confirm before the address becomes the account email).

**Rationale:** The code's own comment names the missing endpoint. Because password recovery is email-based (forgotten flow), changing to a well-formed but unowned/mistyped address can permanently lock the user out of their account — a bounded but real account-safety gap.

## 8. [MEDIUM] Crash reporting / telemetry ingestion — AppResilience captures exceptions that vanish in Release

**Files:** src/ProoveGaming.App/Services/AppResilience.cs, src/ProoveGaming.App/App.axaml.cs, src/ProoveGaming.DeviceHost/Program.cs

**Current state:** No crash-reporting or telemetry SDK anywhere in src/. AppResilience catches all three unhandled-exception sources (Dispatcher, UnobservedTaskException, AppDomain) and reports only via _logger.LogError (line 67) — but the App's logging is AddDebug only (App.axaml.cs line 194), so in Release these go to the Windows debug-output stream nobody reads. DeviceHost writes Serilog locally (Program.cs line 80) but transmits nothing.

**API need:** Crash/error ingestion endpoint (or a third-party sink like Sentry) receiving what AppResilience already captures — exception, source, app version, device roster — with user consent.

**Rationale:** The interception points exist; only the sink is missing. The vendor currently has zero visibility into field failures of an app designed to run for days in the tray — the DeviceHost 23 GB leak class of bug was only found because the developer's own machine hit it. Pairs with app self-update: detection without a fix channel, or vice versa, is half a loop.

## 9. [MEDIUM] Announcement / notification feed — server-pushed messages into the existing bell notification center

**Files:** src/ProoveGaming.App/ViewModels/HomeViewModel.cs, src/ProoveGaming.App/Services/LocalStorageService.cs, src/ProoveGaming.App/ViewModels/NotificationItemViewModel.cs

**Current state:** A complete notification center already ships: owner-scoped bell history in SQLite (capped at 100 per owner, LocalStorageService.cs ~line 2674), date grouping, unread counts, mark-all-read, delete-all (HomeViewModel.cs lines 342-351, 104-107). Every producer is local — the only AddNotification call sites are device connect/disconnect/new-device/low-battery events plus the Contact Us confirmation. Nothing fetches from a server. (The stored rows themselves are per-machine, already-localized history with no cross-device sync value — by design per the schema comment.)

**API need:** Announcement/message feed endpoint (per-locale, optionally filtered by owned device models): product news, firmware-available notices, promotions — polled by the App and merged into the bell via the existing AddNotification path. Not a sync of existing local rows.

**Rationale:** Merged two items; adopted the medium priority because the expensive parts (persistence, grouping, unread tracking, UI) are already built — a feed API is a pure producer plugged in. It is also the natural delivery channel for firmware-update and app-update notices, multiplying the value of those two high items.

## 10. [MEDIUM] Remote device catalog / feature flags — DeviceHost AllowedDevices and per-device defaults are baked into the installer

**Files:** src/ProoveGaming.DeviceHost/appsettings.json, src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.cs

**Current state:** The supported-device list and factory defaults live in DeviceHost's local appsettings.json (AllowedDevices section from line 37: per-model Dpi 1200, ReportRateHz 1000, RgbEffect 'Breathing', RgbColorHex '#7620EE', ...), bound via IOptions<AllowedDevices>. No runtime refresh mechanism exists — supporting a newly released peripheral or correcting a bad shipped default requires building and manually distributing a new installer.

**API need:** Remote-config endpoint: versioned device-catalog + defaults document (plus simple feature flags) fetched by DeviceHost/App at startup, with the local appsettings.json as offline fallback.

**Rationale:** Proove actively ships new peripherals (Taipan, Starlight, Cosmo work visible across the repo), and with no self-update path today a hardcoded catalog gates every product launch on user reinstalls; a wrong shipped default is otherwise permanent on installed machines. Cheapest escape hatch until self-update exists.

## 11. [LOW] Device roster / registration — cloud list of a customer's devices for warranty, support pre-fill, and fresh-install cards

**Files:** src/ProoveGaming.App/Services/LocalStorageService.cs, src/ProoveGaming.App/ViewModels/HomeViewModel.cs, src/ProoveGaming.App/Services/AuthApiService.cs, src/ProoveGaming.App/ViewModels/DeviceCardViewModel.cs

**Current state:** The devices table is owner-scoped local SQLite (guest rows rewritten whole by Flush; user rows written per change — LocalStorageService.cs lines ~100-116, APIs at 2493-2674) backing the Home device cards. No backend endpoint mentions a device; nothing transmits which peripherals a customer owns (full surface enumerated in AuthApiService.cs lines 24-79). Devices are identified by vid/pid + deviceKey; per-unit identity is weak — HidIdentityProbe.cs line 17 notes the USB serial string is not populated by the firmwares, so registration would be model-level.

**API need:** Optional authenticated device-roster/registration endpoint: on connect of a recognized device while signed in, register model + name + device_key + connect date (+ firmware rev once readable) to the account — feeds warranty lookup, support pre-fill (enriching contact_us), fresh-install card display, and install-base analytics.

**Rationale:** Merged two low items. Cards rebuild from live discovery so nothing breaks without it; value is mostly business-side, and weak per-unit identity limits it to model-level registration. Cheap to add once any authenticated device-aware endpoint exists.

## 12. [LOW] Preset/macro export, import and sharing

**Files:** src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.Presets.cs, src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.MacroRecorder.cs, src/ProoveGaming.App/ViewModels/DeviceDetails/DeviceDetailsViewModel.Buttons.cs

**Current state:** Presets support create/duplicate/switch/reset entirely against local SQLite; macros are recorded in-app and saved via _localStorage.SaveMacro (Buttons.cs line 613). Grep finds no export, import, file-based, or online sharing capability of any kind — presets and macros cannot leave the machine even as a file.

**API need:** Sharing service: upload a preset/macro to a shareable link or browsable library and import community/vendor-curated ones (Chroma Workshop as reference). A file export/import format is the client-side prerequisite.

**Rationale:** Real parity gap with the big suites and a community lever, but it depends on the settings-sync data model (item 1) existing first, and nothing in the shipped UI promises it today. Worth designing the sync schema so shared objects are the same shape.

## 13. [LOW] Avatar — upload/replace only, no server-side removal

**Files:** src/ProoveGaming.App/Services/AuthApiService.cs, src/ProoveGaming.App/ViewModels/ProfileViewModel.cs

**Current state:** The only avatar endpoint is POST api/profile/avatar (AuthApiService.UploadAvatarAsync lines 81-111, with FILE_TOO_LARGE / INVALID_FILE_TYPE handling in ProfileViewModel 445-446). Grep for any remove/delete-avatar path finds nothing server-facing; the only deletion is the locally cached avatar file on sign-out (ProfileViewModel 288-301).

**API need:** Avatar-delete endpoint, or api/profile/update support for clearing the avatar field.

**Rationale:** Bounded: replace works, remove does not exist anywhere in the client surface. Whether the UI offers 'remove' today determines if this is even user-visible.

## 14. [LOW] Newsletter preference — server sends state the client discards; no post-registration write path

**Files:** src/ProoveGaming.App/Services/CustomerDto.cs, src/ProoveGaming.App/ViewModels/ProfileViewModel.cs, src/ProoveGaming.App/Services/AuthApiService.cs

**Current state:** CustomerDto.Newsletter (line 35) is deserialized from api/profile but never consumed — ProfileViewModel.LoadProfile (lines 174-180) skips it. The preference is written exactly once, as agree_newsletter at registration (AuthApiService.cs line 37); api/profile/update's body (lines 61-70) has no newsletter field, so it cannot be changed after sign-up.

**API need:** Newsletter field on api/profile/update (or a dedicated preferences endpoint) plus a Profile toggle, if the subscription should be user-manageable post-registration.

**Rationale:** One-way, set-at-registration-only preference grounded in grep. Minor, but potentially a compliance nicety (marketing-consent withdrawal currently requires leaving the app).

## 15. [LOW] Server-side sign-in lockout enforcement (local auth cache is otherwise correctly out of scope for sync)

**Files:** src/ProoveGaming.App/Services/LocalStorageService.cs, src/ProoveGaming.App/ViewModels/ProfileViewModel.cs

**Current state:** saved_auth, last_sign_in, and sign_in_lockout are intentionally local SQLite (schema lines 117-133; APIs 2805-2958) backed by the existing UsersApi — nickname edits already round-trip through CheckProfileNicknameAsync + UpdateProfileAsync (ProfileViewModel 596-626). The sign-in lockout, however, is enforced purely client-side: deleting proovegaming.db resets it.

**API need:** No sync API — tokens and auth cache must be explicitly excluded from any /api/settings payload. The only plausible server change is rate-limiting / lockout enforcement on api/login server-side, if brute-force protection is meant to be real.

**Rationale:** Mostly a negative/guard finding kept so the settings-sync design (item 1) excludes credentials, plus one security-posture note: a client-local lockout is trivially bypassed, so if it matters it belongs on the server. Two pure-inventory analyst items (AuthApiService endpoint list, gRPC RPC list, error-code coverage check) were dropped from this list as they state no API need; the gRPC note that SetMacrosRequest.device_key is declared but not used for routing (proto lines 434-438) is a DeviceHost client-side gap, not a backend API need.
