# Project glossary (CONTEXT)

Short, one-line definitions of every domain / project term used in this repository.
Whenever a new term appears in code, docs, or plans, add it here in the same change
(see the **Documentation rules** section in `CLAUDE.md`). Keep entries alphabetical,
one line each: `**Term** — definition.`

## Terms

- **Actuation point** — the key-travel depth (mm) at which a magnetic-switch key registers a press; paired with a release point. Adjustable on [[T800]] (RY5088 `0x65`/`0xE5`) and [[Cyrex]]/[[Aress]] ([[Key travel area (magnetic axis)]]); plan: `docs/plans/add-keyboard-actuation/`.
- **Add device card** — the purple "CONNECT YOUR FIRST DEVICE" / "ПІДКЛЮЧІТЬ ПЕРШИЙ ДЕВАЙС" tile on the Home grid (`AddDeviceCardViewModel`). An empty-state prompt, not an action (its command is empty): since 2026-09-30 it is in the grid only while there are **no** device cards at all (a disconnected card counts as a card); `HomeViewModel.SyncAddDeviceCard` removes it when the first card appears and puts it back last when the last card is deleted.
- **Adopt pass / revive pass** — the two halves of `HomeViewModel.ReloadOwnerScopedState`, which re-anchors owner-scoped state after a sign-in or sign-up. The *adopt* pass writes every card currently on screen into the arriving user's `devices` rows; the *revive* pass brings back that user's stored cards that are **not** on screen, so they reappear as disconnected. Since 2026-08-27 the revive pass classifies the row set as it was **before** the adopt pass wrote anything, and decides with the [[Swallow rule]] rather than relying on the adopt pass's deletes having already happened. Plan: `docs/plans/fix-owner-scoped-state-persistence/`.
- **AP colour slot** — value `7` in the low nibble of the [[LED Param Table]] `Option` byte: the one setting that makes [[Rongyuan]] firmware read the packet's R/G/B bytes. Slots `0`–`6` are hard-coded preset colours whose R/G/B is ignored, and `8` is firmware-cycled full colour — so a board sent slot `0` looks stuck on red no matter what the picker says.
- **ApiHttpClient** — the App's shared HTTP envelope helper: owns the single `HttpClient` and the Launcher API base URL, maps transport failures to `IsNetworkError`, and flags a 2xx body that is not the JSON envelope as `MalformedPayload`; `AuthApiService` and [[SyncApiService]] both compose it instead of duplicating the POST/read-response logic. Plan: `docs/plans/add-api-v2-sync/`.
- **AppUpdateInfo** — the App's DTO for the [[Update manifest]] (`version`, `download_url`, `release_notes`; snake_case JSON), carried in [[UpdateCheckService]]'s `UpdateAvailable` event and cached as `LatestKnownUpdate`. Plan: `docs/plans/contact-us-and-update-check/`.
- **AppUpdateManifestUrl** — nullable `ApiSettings` key (`appsettings.json`) pointing at the [[Update manifest]]; empty or absent disables the update check entirely.
- **Advanced-key storage area** — the [[Smart Infinite protocol]] region (read `0x3A` / write `0x3B`, size = Device Info byte 8 × 64) holding variable-length `[TYPE, LEN, payload]` records for the vendor's six advanced key modes (DKS `0x80`, MT `0x81`, TGL `0x82`, SOCD `0x83`, [[Rapid Snap (RS)]] `0x84`, END `0x85`); a participating key's matrix triplet becomes `{TYPE, offset_lo, offset_hi}` pointing into it. Rebuilt whole on every save, written before the matrix. Extracted from [[Keyborder]] — see `docs/knowledge-base/smart-infinite-protocol/advanced-keys-rapid-snap.md`.
- **Advanced-key area reset** — the DeviceHost's recovery from a torn two-region write: when the [[Advanced-key storage area]] no longer parses against the matrix pointers (a dropped `0x18` packet, or a transfer that stopped between the two regions), the next read restores every pointer slot's factory triplet, zeroes the area and reads the board again, so the [[Extended Keys]] section — and the DEFAULT SETTINGS control that rewrites it — stays reachable instead of the board reading as "unsupported" forever. Mirrors [[Keyborder]]'s `restoreWindowsDefaultLayer`; one attempt per read, never a loop. Plan: `docs/plans/add-cyrex-extended-keys/` (round 2, S1).
- **Aress** — a supported wired magnetic-switch 65% keyboard (VID `10473`, PID `12910`). Same [[Smart Infinite protocol]] family as [[Cyrex]]; reports 68 keys in a 75-slot matrix and **accepts key-matrix writes**. Physically the same board as Cyrex — their factory tables differ in exactly three navigation slots (Aress: Insert / Delete / PageDown; Cyrex: Delete / PageDown / End), so the geometry is shared via [[SmartInfinite65Geometry]] and only the catalogs differ.
- **Artwork colourway** — a keyboard artwork that ships more than one keycap finish stacked in the same SVG. The delivered [[T-Racer]] file draws the white-keycap render and then the black-keycap render over it at identical position and size, so only the black one is ever visible. `docs/plans/add-tracer-artwork/split-tracer-artwork.py` removes the hidden one — halving the payload — but re-verifies the occlusion pixel by pixel first and aborts rather than stripping if a future revision stops occluding.
- **Audio volume target** — per-device catalog field (`AllowedDevices:Devices[*]:AudioVolumeTarget`, default `OperatingSystem`) saying **where** a headset's volume is applied: `OperatingSystem` drives that device's own Windows endpoints through Core Audio, `Device` would write a level held in the device's own firmware. [[Cosmo]] is `OperatingSystem`; the `Device` branch is deliberately inert until a headset needs it. A capability rather than a fixed rule because the two are not interchangeable. Travels as `DeviceCatalogEntry.audio_volume_target`.
- **AuthSessionCoordinator** — the App service (`Services/AuthSessionCoordinator.cs`) that owns the session state transitions formerly in `MainWindow`'s code-behind: completing sign-in and registration (guest migration only on registration), logout, sign-out on token rejection, and guest-session expiry. It keeps their order exactly and drives the ViewModels through `IOwnerScopedState`, `IProfileSession` and `IDeviceDetailsExit`; `MainWindow` only navigates. Plan: `docs/plans/refactor-auth-session-flow/`.
- **BatteryChange** — gRPC push (`SubscribeOnDevicesResponse.batteryChange`) carrying a device's battery level the moment the DeviceHost sees it, so the App does not wait up to 60 s for its own poll. `known = false` means no usable reading and the App clears the indicator — for TAIPAN that is the [[Mouse-absent reply]]. Raised by [[TaipanStateMonitor]] only when the value actually changes, since the mouse re-pushes the same level on every link establishment.
- **Bearer Token** — HTTP `Authorization: Bearer {token}` credential required on Launcher API protected endpoints; the token is a [[Session Token]] issued by `POST api/login`.
- **Binary planting** — dropping a file named like a system tool (`sc.exe`, `powershell.exe`, a DLL) where an elevated process will find it first — typically the Downloads folder next to an installer, since `CreateProcess` searches the application directory before `System32`. Countered by starting every system tool by its absolute `System32` path (finding S5). Plan: `docs/plans/fix-repository-audit-findings/`.
- **BLAZE** — a supported wired gaming mouse model built on the Holtek HT68FB571 / Easen platform; the marketing name for the X43. Protocol docs: `docs/mouse/blaze/`.
- **BLAZE LED effects** — the complete set of four firmware lighting effects per the vendor spec: Off (`0x00`), Breathing (`0x02`), Neon (`0x03`), Raindrop (`0x06`). There is no static/direct-RGB effect. See `docs/mouse/blaze/blaze-vendor-qa-2026-07-27.md` and `docs/mouse/blaze/led.md`.
- **BLE address instability** — a PG TAIPAN's Bluetooth LE address **changes every time it is re-paired**: measured `D10B779C83C4` → `D10C779C83C4` → `D10D779C83C4` across three remove/re-add cycles (2026-08-25). It is therefore NOT a stable per-device identity across pairings. This broke reconnect twice over: `DeviceMap.DeviceId` cached the address from the first pairing and `DeviceNeedToTrack` only filled it when empty, so after a re-pair `GetClientName(deviceId)` matched nothing and the connection event went out with an **empty ClientName** — which the App silently discards, because it matches its card by that string. Both the stale cache and the blank-name path are fixed (see [[BLE presence poll]]), but anything else keying a BLE device by address across pairings — settings buckets, `MergeTransports`, saved presets — should be treated as suspect until checked.
- **BLE presence poll** — the 3 s device-tree check in `BluetoothDeviceDiscoveryService.PollLowEnergyPresence` that marks a low-energy device disconnected once it stops having a present `BTHLE` node reporting `DEVPKEY_Device_IsConnected`. Added 2026-08-20: BLE disconnects were previously only noticed by the 30 s `ActiveSweepInterval` (5 min when idle), so a switched-off Bluetooth mouse showed as connected for 20 s+. Since 2026-09-08 it is also what makes the sweep's own backoff safe — the sweep escalates to 5 min only while this poll has a working snapshot, and a disconnect it detects now opens a scan window itself instead of waiting for one. Node **absence** (pairing removed in Windows) and `IsConnected=false` (device switched off) are the same signal — both measured on a PG Taipan. **Bidirectional**: it marks a device connected as well as disconnected, and `RegisterDevice` defers to it via `ResolveConnected` — `Gatt.IsConnected` reflects our GATT client, not the OS link, and is wrong both ways (stale `true` once the radio is off; stuck `false` on the dead instance left after a device is removed and re-paired, which left the card offline until an App restart). A `null` tree opinion means *no opinion* and must never read as disconnected. Treats a failed enumeration as no evidence rather than as absence, and requires two consecutive misses (~6 s) before disconnecting so a radio blip cannot show a working mouse as absent; reconnect acts on the first poll. A device whose node is **absent** (removed in Windows, as opposed to merely switched off) is not just marked disconnected but **released** — `ReleaseTrackedDevice` drops the GATT link, disposes the instance and untracks it. Without that the host kept an open GATT connection to an unpaired device: battery reads still succeeded, `IsPaired` still reported true, and the advertisement watcher kept reconnecting, so the card resurrected itself within seconds of every disconnect. Re-pairing is picked up by a tree-triggered rediscovery (catalogued devices only, one in flight) which re-runs the paired enumeration to build a FRESH instance — the step that was missing, and why a re-added device previously needed an App restart. That rediscovery is rate-limited by an escalating schedule (10 s → 30 s → 5 min, reset the moment a poll finds nothing unexplained) rather than the flat 10 s cooldown it shipped with: the cooldown was not a bound, because a device the enumeration can never resolve leaves the trigger armed forever, and each pass is a full `DeviceInformation` enumeration on the Device Association Framework path (see [[Device Association Service]] and `docs/audits/2026-09-02-device-association-memory-audit.md`). Complements the classic-Bluetooth poll of the same cadence.
- **Bluetooth mode banner** — the "BLUETOOTH MODE" info block (`BluetoothModeBannerView`) shown at the top of every device-preview panel on the details page while the live transport is a Bluetooth link that cannot carry configuration (`IsBluetoothConfigLocked = HasBluetooth && !SupportsConfiguration`, catalog-driven), telling the user settings are unavailable over Bluetooth and to connect via dongle or cable. The same condition disables every section panel (dimmed via the shared `bluetoothLocked` class) and the header preset controls. Headsets (Cosmo, Starlight) are exempt since ticket 2026-09-02 — their audio targets the OS endpoint, so they configure fine over Bluetooth and never lock — superseding the uniform read-only Bluetooth mode of 2026-08-30, which keyboards/mice keep via `SupportsConfiguration: false` on their Bluetooth catalog rows. The key-assignment read-failed warning stays suppressed on `HasBluetooth` (transport truth, not configurability). The write-side guard remains `SupportsConfiguration`/`IsDeviceConfigurable`. Plans: `docs/plans/add-bluetooth-mode-banner/`, `docs/plans/remove-headset-bluetooth-lock/`.
- **BluetoothName** — per-transport catalog token (`AllowedDevices:Devices[*]:Transports[*]:BluetoothName`) naming a case-insensitive substring of the Windows device name, used to tell apart products that share one classic-Bluetooth VID/PID. [[Starlight]] and [[Cosmo]] both report `0x05D6/0x000A` (measured 2026-08-19), so the id pair is an ODM constant like their byte-identical USB `iSerialNumber` — while `MatchCatalog` keyed on ids alone it took the first matching row and drew a connected Starlight as a **Cosmo card**. A row matching by token outranks an untokened one; a row with no token keeps id-only matching, so TAIPAN / Rampage / T-Racer are unaffected. Trade-off: a device the user RENAMES in Windows stops matching. Plan: `docs/plans/add-starlight-bluetooth/`.
- **BtFuncNum** — the first byte of a TAIPAN button-map entry; `bit7` marks the entry active and `& 0x7F` selects the function (left click, DPI cycle, macro, …). See `docs/mouse/taipan/protocol.md`.
- **APO (Audio Processing Object)** — a Windows user-mode DSP plug-in Windows loads into an audio endpoint's stream when an *extension INF* binds it to that endpoint. C-Media's is **CMAPO_ICE** (`CmApoIce.dll`) and it is what actually computes every [[Xear]] effect — EQ, noise reduction, surround. Two things must both be true for those effects to exist on a device: the APO is installed and bound for that VID/PID, and the [[Xear license category]] is granted. Neither holds for [[Starlight]]. See [[CmXearSDK]].
- **Card identity** — the one rule that decides whether two device cards (or a card and a stored `devices` row) are the same device: for a [[merge_transports]] product the upper-cased name alone, for everything else `(name, vendor_id, product_id, device_key)`. Defined once as `HomeViewModel.CardIdentity` and used by discovery's card matching, the revive pass in `ReloadOwnerScopedState` and `LocalStorageService.AddDevice`'s dedupe, so storage and UI can never disagree — when they did, a Rampage on Bluetooth stored a second row and it came back as a permanent "NO CONNECTION" card. See `docs/plans/fix-duplicate-device-cards/`.
- **Card status row** — the shared `CardStatusRowView` (`src/ProoveGaming.App/Views/`): the centered status line under a device card's name — transport icons, audio-mute indicators, battery icon/percentage, "NO CONNECTION" — hosted by both `SingleCard` and `DoubleCard` and carrying the connection tooltip itself. Extracted from the single card's row after the double card's fixed-coordinate copy rendered short icon combinations off-center. See `docs/plans/fix-card-status-icons-centering/`.
- **Chain generation (`_setDeviceGeneration`)** — a counter `DeviceDetailsViewModel.SetDeviceAsync` bumps on every device open; the awaited loader chain and each async loader drop their apply when the generation moved on, which catches stale runs `ReferenceEquals(Device, …)` cannot — reopening the *same* card while its previous load is still in flight. See `docs/plans/fix-details-navigation-delay/`.
- **ClientErrorCodes** — `error_code` values the App's [[ApiHttpClient]] sets itself when a request got no usable answer (`CLIENT_NETWORK_ERROR`, `CLIENT_TIMEOUT`, `CLIENT_INVALID_RESPONSE`); the server never sends them, and they are kept apart from `AuthErrorCodes`, which is the server's catalog. `ApiErrorMessages.Describe(response, fallbackKey)` turns them, a rate limit, or a caller fallback into localized text, so no exception or server English reaches the UI (findings S10/A8). Plan: `docs/plans/fix-repository-audit-findings/`.
- **CM002X1** — the C-Media crypto coprocessor reached over I2C (slave address `0x7A`) through a transparent HID↔I2C bridge on report `0xFD`, used solely for [[Xear]] licensing; the headset firmware bridges HID↔I2C and does not interpret the payload. Carries no RGB, volume or battery data. Present on [[Cosmo]] **and — confirmed 2026-09-09 — on [[Starlight]]**, where it was previously believed absent. Reads are a two-step request/response (`0x11` I2C write, `0x12` I2C read, `0x13` return data), which is why a bare input-report read returns zeros; see [[Starlight vendor channel]]. Vendor guide: `docs/headset/cosmo/`.
- **Change Password flow** — the signed-in Profile → Security action; since 2026-08 it reuses the [[Password reset flow]]: an in-app dialog (email pre-filled from the account) posts to `api/forgotten` and the new password is set on the website via the emailed link. `api/profile/password_link` is no longer called by the launcher. Plan: `docs/plans/refactor-change-password-flow/`.
- **CmXearSDK** — C-Media's C API (`CmXearSDK.dll`, V1.0.28.0) for reading and setting audio-endpoint properties and [[Xear]] effects, supplied with a WPF demo app and an API reference. Splits into a **non-APO** half (identity, format, volume, peak level, default-device role, foreground process, device events, play-a-file) that is Core Audio underneath and works anywhere, and an **APO** half (~170 effect properties) gated by [[APO (Audio Processing Object)]] binding and licensing. Evaluated on Starlight hardware 2026-09-09 and **not integrated** — the working half duplicates `AudioEndpointService`, the rest is locked. It has **no LED, battery or power-state API**. Findings: `docs/headset/starlight/starlight-research-2026-09.md`. Probe: `starlight xear`.
- **Config frame ACK** — TAIPAN's reply to each frame of a sequenced configuration write: the frame echoed back with `driverPara4` (the [[SeqFirst]]/`0xD2`/`0xD3` sequencing byte) zeroed and the checksum recomputed over the modified header. Measured 2026-08-18 — the **cable ACKs all 8 frames** of a button-map write, the **2.4G dongle ACKs none** while still answering the battery query `0x48` on the same stream, and the remap only takes effect on the cable. `TelinkMouseService.WriteFrameAsync` never reads, so the app has always discarded these on both transports. Evidence: `docs/mouse/taipan/taipan-dongle-ack-evidence-2026-08-18.md`.
- **Contact Us dialog** — the 620×524 modal opened from the Home header's profile/guest dropdowns: email (pre-filled from the signed-in profile) + topic (≤100 chars) + message (≤2000 chars) with live counters, SEND disabled until valid; posts to `api/contact` (API v2.0). Plan: `docs/plans/add-contact-us-dialog/`.
- **Contact Us anti-spam window** — `api/contact`'s three server-side limits (v2.0 §20): one successful message per 60 s, five per 24 h, and identical topic+message blocked as a duplicate for 10 minutes; each has its own `error_code` and its own user-facing wording.
- **ContactUsErrors** — `src/ProoveGaming.App/Services/ContactUsErrors.cs`: maps an `api/contact` failure envelope (or HTTP 429) onto the resource key the dialog's single error line shows, scanning every `errors[]` entry by priority. Mirrors `ForgottenPasswordErrors`.
- **DeviceHost pipe** — the Windows named pipe `\\.\pipe\ProoveGaming.DeviceHost` that carries App ↔ [[DeviceHost]] gRPC, replacing the TCP port 5000 endpoint of builds before 2026-09-24. Its ACL admits SYSTEM, Administrators, interactive users and the host's own account (needed to create further pipe instances), denies network logons, and is closed to AppContainers and low-integrity processes. The name is one constant (`DeviceHostPipe.PipeName` in GrpcDependencies) shared by the App, the host and the Checker. Plan: `docs/plans/migrate-devicehost-named-pipe/`.
- **DisplayName (catalog)** — optional field on a DeviceHost catalog row (`appsettings.json`) with the name the App shows for that device when it differs from `Name`; `Name` stays what device matching, storage and protocol choice key on. Used by PG TAIPAN, shown as TAIPAN MAX.
- **Embedded appsettings** — the App's and the DeviceHost's `appsettings.json` compiled into their assemblies as embedded resources instead of shipped as files, so an install has no settings file to read or edit; changed in the repository only. DeviceHost side: `EmbeddedAppSettings`.
- **Pipe server verification** — the App's check that the process serving the [[DeviceHost pipe]] is the real `ProoveGamingDeviceHost` service: the pipe's server PID (`GetNamedPipeServerProcessId`) must equal the PID the Service Control Manager reports for the service. A process that creates the pipe name first can then only deny service, never impersonate the host. Relaxed in Debug builds so a console-run host works. Plan: `docs/plans/migrate-devicehost-named-pipe/`.
- **ProtoInput** — the [[DeviceHost]]'s normaliser for untrusted gRPC input (`Helpers/ProtoInput.cs`): clamps macro key codes and delays, rejects a request naming an undefined button, action or repeat mode, and caps a macro at 256 events. Every RPC that maps a macro or a button binding goes through it (finding S9). Plan: `docs/plans/fix-repository-audit-findings/`.
- **Rate limit (429)** — HTTP 429 Too Many Requests, documented across API v2.0. Surfaced transport-level as `ApiResponse.IsRateLimited`; interactive callers show the shared `Api_Error_TooManyRequests` string, the sync pass aborts and sits out a cooldown.
- **Retry-After** — the RFC 9110 response header carried on a 429 in either delta-seconds or HTTP-date form; parsed once in `ApiHttpClient` into `ApiResponse.RetryAfter` (never negative) and used as the sync cooldown length.
- **Profile auto-save toast** — the notification raised when the debounced inline profile save (first/last name, telephone, country, date of birth) is rejected. The typed value deliberately stays on screen; a revert would re-enter the `PropertyChanged` handler. Plan: `docs/plans/improve-api-error-surfacing/`.
- **ContactUsOutcome** — the two-way result of a Contact Us send (`Delivered` / `Failed`) decided by the static `HomeViewModel.DecideContactUsOutcome`: a 2xx success envelope → the "sent" wording; anything else (network error, 404, 5xx, malformed 2xx, success:false) → the dialog stays open with an error. The former `AcceptedRouteMissing` degraded mode was retired when API v2.0 documented `api/contact` (`docs/plans/add-api-v2-sync/`) Since `docs/plans/improve-api-error-surfacing/` the `Failed` branch carries per-code wording chosen by **ContactUsErrors** rather than one generic string.
- **Container ID** — the Windows `DEVPKEY_Device_ContainerId` GUID; identical across one physical device's HID interfaces and unique per device, used as the app's per-device identity key (`deviceKey`).
- **Cosmo** — a supported gaming headset (VID `0x0D8C` C-Media / PID `0x0334`, "THI Headphone" / "PG Cosmo"). USB composite: `MI_00` is USB Audio Class (the Windows "Headphones (PG Cosmo)" / "Microphone (PG Cosmo)" endpoints), `MI_03` a single HID interface. Unlike BLAZE and TAIPAN it reports a real USB `iSerialNumber`, so its [[Container ID]] is stable across USB ports — but that serial (`00006F64096B22E7`) is **byte-identical to [[Starlight]]'s**, so it is an ODM firmware constant and not a per-unit identifier. Its volume keys are standard consumer-control keys Windows already handles. Connects over a **2.4G dongle** (`Dongle2_4G`). Its power (on/off) state comes from [[Cosmo status report]]; that report carries **no battery**, so the dongle transport sets `SupportsBattery: false` and a level is shown only over Bluetooth (GATT). Plan: `docs/plans/add-cosmo-headset/`.
- **Cosmo status report** — [[Cosmo]]'s vendor HID report `0xBC` (usage page `0xFF02`). The dongle **pushes nothing** on it — a full guided capture produced zero frames — so it is read with `HidD_GetInputReport`, a control-transfer READ, never a write. Byte 19 is **confirmed**: `0x03` = headset on, anything else = off (the sole offset that moved across a power cycle). It carries **no battery**: byte 17 (`0x57` = 87) and bytes 20-21 (3764 mV) were each published as the level and each disproven on 2026-09-03 — byte 17 read 87 while the same headset reported 40 % over Bluetooth, and the millivolts did not move a single bit as it discharged 40 % → 30 %. `BatteryPercent` is now always null and Cosmo's `Dongle2_4G` transport sets `SupportsBattery: false`; the millivolts are parsed for diagnostics only. Microphone mute is not carried here or anywhere the host can see. `CosmoStateReport` / `CosmoStateReader` in `ProoveGaming.Infrastructure`. Microphone mute is not carried here or anywhere the host can see. `CosmoStateReport` / `CosmoStateReader` in `ProoveGaming.Infrastructure`.
- **CountrySelectView** — shared Avalonia control (`ProoveGaming.Common/Controls`) rendering the profile Country field: a header row plus a dropdown of every OS-known country except the excluded regions (RU, BY, KP). Rows are built on first open, not at construction.
- **Borrowed overlay artwork** — the Key Assignments / Macros key overlay renders `DeviceDetailsViewModel.KeyOverlayArt`, which is normally the device's own [[RgbKeyboardArt]] but resolves to Cyrex's for [[Aress]]. Deliberately separate from `KeyboardArt`, which still drives the RGB backlight preview and the home card: those want the artwork the device ships with, the overlay wants the one whose keycaps match the measured bounds, and for Aress those are two different files.
- **Cyrex** — a supported wired magnetic-switch 65% keyboard (VID `10473` / `0x28E9`, PID `12914` / `0x3272`). Member of the [[Smart Infinite protocol]] family; reports a 75-slot key matrix of which 7 slots are unused placeholders, giving 68 real keys, and **accepts key-matrix writes** — the first device in this family where remapping works. Catalog generated from the device's own factory table (`CyrexKeyCatalog`).
- **CyrexArtworkLayout** — keycap bounds measured from the [[Cyrex]] artwork, in that artwork's viewBox coordinates and keyed by [[Matrix slot]], so key overlays sit on the rendered board instead of an idealised grid. Derived by connected-component labelling of the keycap layer; the pass finds 68 components against 67 remappable slots, the extra being FN. Aress has no counterpart table and reuses this one: its own shipped artwork does not depict the Aress board (16 keys across the top rows against the board's 15), but the two are the same physical board, so Aress renders the Cyrex artwork here and joins this table against its own catalog by slot. See [[Borrowed overlay artwork]].
- **DatePickerView** — shared Avalonia control (`ProoveGaming.Common/Controls`) rendering the profile Date-of-Birth field: a header row plus a calendar popup whose [[Picker mode toggle]] cycles day → month → year grids. The field shows the selected date as `DD/MM/YYYY`; every string inside the popup (weekday headers, month names) comes from [[DatePicker resource keys]], re-read on each render so it follows the app language.
- **DatePicker resource keys** — the three key tables in `ProoveGaming.Common/Localization/DatePickerResourceKeys.cs` (7 weekday abbreviations, 12 short and 12 full month names) that [[DatePickerView]] resolves through [[ResourceStrings]]. Values are stored already uppercased so each language controls its own casing, and full month names must be nominative because the popup header shows the month standalone.
- **Default preset** — the single row per (owner, device type — VID/PID) with `is_default = 1`. Shared across every physical unit of that model, distinct from [[deviceKey]]/[[Container ID]]-scoped live device state (RGB, button bindings, which preset is currently applied), which stays per physical unit. Auto-created on first device open when the preset list is empty; the Delete kebab entry is disabled on this row and both the ViewModel command and `LocalStorageService.DeletePreset` refuse to delete it. Managed by `LocalStorageService.PromotePresetToDefault` (single transaction demote-siblings-then-promote-target).
- **Seed-vs-pull ordering** — the rule that a signed-in user's [[Default preset]] seed (`CreateDefaultPresetIfNotExists`) must not run until the sign-in pull has settled (`ISettingsSyncService.PullTask` awaited in `DeviceDetailsViewModel.LoadPresetsForDeviceAsync`): an "empty" scope may just be the pull in transit, and a seed there mints a fresh-uid default the pull cannot dedup, which then accretes on the server. Its offline backstop: the pull's default arbitration deletes a never-synced (`server_updated_at IS NULL`) local default in favour of the server's (`LocalStorageService.DeleteNeverSyncedPreset`, no tombstone). Guests never pull and never wait. Plan: `docs/plans/fix-duplicate-default-preset/`.
- **Device defaults** — the optional `Defaults` block on a catalog device (`AllowedDevices:Devices[*]:Defaults` in the DeviceHost `appsettings.json`), carried to the App on `DeviceCatalogEntry` and surfaced as `DeviceCardViewModel.Defaults`. Holds that model's factory-sane DPI, report rate, debounce, lift-off and lighting; consulted when a device is first used and by the DPI "Recommendations" and Settings "Restore to default" buttons. Every field is optional and an omitted field falls back to an app-wide constant. Values and rationale in `docs/device-defaults.md`.
- **Mod-Tap (MT)** — [[Extended Keys]] single-key mode `0x81`: one physical key outputs a *hold* key when held ≥ a threshold in ms and a *tap* key when released sooner; record `[0x81, 6, time16, holdType, holdCode, tapType, tapCode]`. Plan: `docs/plans/add-extended-key-mod-tap/`.
- **Mouse-absent reply** — a well-formed TAIPAN battery reply (`0x48`) carrying a **zero** reading, which the 2.4G dongle returns when no mouse is behind it — switched off, out of range or flat. Measured 8/8 in each state (2026-08-14): the dongle always answers, so *silence* is not the signal and a zero reading is. `TaipanStateReport.IsMouseAbsentReply` validates shape and checksum before believing it, so a corrupt frame cannot clear a good level. See `docs/mouse/taipan/protocol.md`.
- **RequestThrottle** — `ProoveGaming.Infrastructure` helper bounding how often a device is asked something, claiming each time slot with an atomic compare-exchange rather than a read-then-write (which let concurrent callers all pass). One instance serves several cadences over one clock, so [[TaipanStateMonitor]]'s slow periodic battery pass and its on-demand refresh cannot double up on the same mouse.
- **ServiceControl** — `ProoveGaming.Common` runner for `sc.exe`, shared by the installer and uninstaller. It starts the tool by its absolute `System32` path (see [[Binary planting]]), drains stdout and stderr concurrently so a chatty child cannot deadlock it, and reports the exit code, which is the only thing decisions are made on (sc.exe's text is localised). `SystemTool` beside it gives the rooted paths for `powershell.exe` and `cmd.exe` (findings S5, A2). Plan: `docs/plans/fix-repository-audit-findings/`.
- **SupportedAudioSettings** — per-device catalog list (`AllowedDevices:Devices[*]:SupportedAudioSettings`) naming the audio levels a device exposes: `OutputVolume`, `MicrophoneVolume`. Non-empty only on headsets, and it is what makes the details view's Audio section appear — the sliders are built from this list, so a device that declares none never shows the section. Persisted as `audio.outputVolume` / `audio.micVolume` rows in `device_settings`, which is how the values join preset snapshots alongside debounce and lift-off. See [[Audio volume target]] for where the level is applied.
- **SupportsBattery** — per-device catalog flag (`AllowedDevices:Devices[*]:SupportsBattery`, default true) saying whether the device has a battery the app can actually **read**. The battery indicator is otherwise inferred purely from the transport (a dongle implies a battery), so a wireless device with no way to read one would show a red "critical" icon. Added for [[Cosmo]] and currently set by no device — Cosmo's battery turned out to be readable after all (see [[Cosmo status report]]). Kept for the next wireless device that genuinely cannot report a level. Travels as `DeviceCatalogEntry.battery_unsupported` (negated so an older DeviceHost still reads as "battery works"), same convention as [[SupportsConfiguration]].
- **SupportsConfiguration** — per-transport catalog flag (`AllowedDevices:Devices[*]:Transports[*]:SupportsConfiguration`, default true) saying whether host→device configuration actually reaches the hardware over that transport. False for [[TAIPAN]] on its 2.4G receiver and on Bluetooth, where writes are accepted and never applied (`docs/mouse/taipan/taipan-dongle-config-findings-2026-08-04.md`; refined 2026-08-18 — the dongle does not even [[Config frame ACK]] those writes, see `taipan-dongle-ack-evidence-2026-08-18.md`). Travels as `DeviceCatalogEntry.configuration_unsupported` (negated so an older DeviceHost reads as "supported") and keeps the App's Save Preset button disabled on those transports.
- **Device roster** — the [[Launcher API]] v2.1 per-account device list (`api/devices/add|list|remove`): one server row per device **model** the customer owns, keyed by settings-identity VID/PID (never [[deviceKey]] — identical units collapse, like device state); `devices/list` also returns each model's `active_preset_uid`. Plan: `docs/plans/add-api-v21-device-roster/`.
- **DeviceHost** — the `ProoveGaming.DeviceHost` Windows Service that owns HID/Bluetooth device I/O and exposes it to the App over gRPC.
- **GetDeviceCatalogEntry** — unary gRPC RPC on [[DeviceHost]] resolving a `DeviceCatalogEntry` by VID/PID with no live device behind it (a thin delegation to `HidDeviceMapRegistry.FindCatalogEntryByPidVid`). Consumed by the App's `IDeviceCatalogResolver` so the sign-in pull can hydrate an offline card for a [[Device roster]] model this machine has never seen. Plan: `docs/plans/add-api-v21-device-roster/`.
- **deviceKey** — the app-wide opaque per-physical-device identity string (a Container ID); empty means unknown/legacy and falls back to single-device behaviour. Hardware-tested 2026-08-04: neither TAIPAN nor BLAZE reports a USB serial number, so Windows derives their [[Container ID]] from the USB port and the key changes when the device is moved — see `docs/device-identity.md`.
- **Instant Release (SOCD)** — [[Extended Keys]] pair mode `0x83`: when both keys are held past actuation the firmware resolves them by a priority carried in the record's LEN high nibble — 0 last input, 1 mutual cancel, 2 Key 1 wins, 3 Key 2 wins (`LEN = priority << 4 | 6`). Plan: `docs/plans/add-extended-key-socd/`.
- **Key Assignment Dialog** — the modal per-key popup (title "<KEY> button", tabs KEYS / SYSTEM / MACROS, RESET, ✕) that opens when a key is clicked on the interactive on-screen keyboard in the Key Assignments or Macros sections; consolidates key remapping and macro binding into one surface, replacing the old inline target list. Plan: `docs/plans/add-key-assignment-popup/`.
- **Output-key picker** — the [[Key Assignment Dialog]] opened in its `PickExtendedKeyOutput` purpose by the Extended Keys single-key editor ([[Mod-Tap (MT)]] and [[Toggle (TGL)]]): KEYS tab only, title "Choose the Hold / Tap / Toggled key", and a pick returns the key's matrix-record triple to the editor instead of staging a remap or writing the board. Plan: `docs/plans/add-extended-key-mod-tap/`.
- **Remap toast** — the auto-hiding "«key» successfully remapped to «target»" notification with an UNDO link, raised after a [[Key Assignment Dialog]] pick commits; it appears only after the device write succeeds (never optimistically), and UNDO restores whatever binding the pick displaced. Implemented in `DeviceDetailsViewModel.KeyDialog`.
- **Key count** — byte 6 of the [[Smart Infinite protocol]] Device Info block: the number of remappable keys the firmware exposes. Cyrex reports 68 and `SmartInfiniteKeyMappingService` reads it before writing, refusing when it is zero. **Not authoritative on [[Rampage]]**: it reports 0 yet accepts the [[RM1]]-shape write (bare `0x18`, full 384 bytes) — which is why Rampage keeps its own `RampageKeyboardKeyMappingService` that skips this gate. Device Info under-reports generally on this family (see [[Macro space]]); the factory's C8 table sizes outrank it for transfer sizing.
- **Key matrix record** — one key's 3-byte assignment `{TYPE, CODE_L, CODE_H}` in a [[Smart Infinite protocol]] table. For `TYPE=0x10` (plain keyboard key) `CODE_L` is the modifier bitmask and `CODE_H` the HID usage code, so Left Shift is `{0x10, 0x02, 0x00}` and a key is identified by the (mask, usage) pair, never by usage alone. Modelled by `KeyMatrixRecord`.
- **Matrix slot** — the fixed firmware position of a physical key inside a key-matrix table; its byte offset is `slot x 3`. Slot counts differ per model (Cyrex 75, Rampage 128). On Cyrex/Aress they come from Device Info; on [[Rampage]] they are compile-time constants taken from the vendor's factory table (`RampageKeyCatalog`), because its Device Info under-reports (see [[Key count]]).
- **Medium integrity** — the Windows integrity level of an ordinary, non-elevated process. Anything such a process can write (`HKCU`, `%TEMP%`, command-line arguments, a user-writable folder) must be treated as untrusted input by the elevated installer, uninstaller and the `LocalSystem` [[DeviceHost]] — the UAC boundary the audit's S1–S5 findings cross. Plan: `docs/plans/fix-repository-audit-findings/`.
- **Rampage** — a supported wireless mechanical TKL keyboard (VID `10473` / `0x28E9`, PID `12888` / `0x3258`). [[Smart Infinite protocol]] family; 96 populated keys in a 128-slot matrix. **Key remapping works** as of the [[RM1]] factory update of 2026-08 (confirmed on hardware): the write is a bare `0x18` transfer of the full 384-byte table, no `0x10`/`0x11` bracket. Its Device Info still reports a [[Key count]] of 0, so it uses a dedicated `RampageKeyboardKeyMappingService` instead of the shared key-count-gated one. **Macros are catalog-enabled** on the [[Macro upload (Smart Infinite)]] path: [[Keyborder]] registers this PID on the same `GamingKeyboard2` protocol with the shared macro UI, its Device Info reports a 2048-byte [[Macro space]], and its bindings take the family's `0x50`/`0x51` records — pending its first hardware run (the upload's authoritative read-back verify fails safely if the firmware declines). See `docs/knowledge-base/rampage-keyboard-protocol/`.
- **Smart Infinite battery monitor** — `SmartInfiniteBatteryMonitor`, the `ProoveGaming.DeviceHost` background service (third sibling of [[TaipanStateMonitor]] and CosmoStateMonitor) that polls the `0x1F` battery reply every 3 s for catalog dongle rows with a usable `BatteryCommand` ([[Rampage]]'s 2.4G receiver today) and pushes level/charge changes through [[BatteryChange]], so the card's ⚡ follows the charging cable in seconds instead of the App's 60 s poll; charge-flag flips are debounced over two agreeing reads, and every tick stays in process memory except the single HID exchange (no Device Association Framework, ever).
- **Smart Infinite checksum** — bytes 5-6 of every [[Smart Infinite protocol]] packet: a plain 16-bit little-endian **additive sum** of `cmd + addr_lo + addr_hi + len` plus every payload byte. Not a CRC despite the vendor sheet labelling it CRC16; verified against the vendor packet captures.
- **Smart Infinite device gate** — the process-wide lock (one `SemaphoreSlim` per `DevicePath`) that serialises access to a [[Smart Infinite protocol]] vendor interface. The firmware allows one session per interface and every service brackets its work in `0x10` … `0x11`, where the closing packet ends the session for the *interface*, not for the sender — so key mapping and the RGB services must share this gate or one silently truncates the other's session.
- **Smart Infinite protocol spec** — the vendor workbook `docs/软件驱动协议-20251028-V3.1.xlsx`, translated to English in `docs/knowledge-base/smart-infinite-protocol/`. Its **data formats** (key record, macro buffer, action-type bits) match our hardware; its **command numbering** is a later revision than our firmware and disagrees with measured values, so commands from it must be verified, never trusted.
- **Smart Infinite receiver channel (`0xAA`)** — the [[Smart Infinite protocol]] family's only documented wireless-config path: the driver talks to the **2.4G receiver** with magic byte `0xAA` (identity handshake `AA 10`, state query `AA D0 …`), and table transfers over 2.4G use 24-byte payloads instead of wired's 56. Bluetooth has no host protocol at all on this stack. See `docs/knowledge-base/smart-infinite-protocol/wireless-receiver-protocol.md`.
- **Extended Keys** — the product name for the [[Smart Infinite protocol]] "advanced key" behaviours of [[Cyrex]]/[[Aress]] and their details-page section: [[Rapid Snap (RS)]] `0x84`, [[Instant Release (SOCD)]] `0x83`, [[Mod-Tap (MT)]] `0x81`, [[Toggle (TGL)]] `0x82`. All live in the [[Advanced-key storage area]], are read/written as one set (`GetExtendedKeys`/`SetExtendedKeys`), and are preset-scoped via `device_extended_keys` / `preset_extended_keys`. Plans: `docs/plans/add-cyrex-extended-keys/` (+ `add-extended-key-socd`, `-mod-tap`, `-toggle`).
- **Extended-keys self-heal** — the step at the end of a device page open that compares the board's managed [[Extended Keys]] records against the signed-in owner's own rows and writes the owner's when they differ. Answers "does the board match this owner" instead of enumerating the transitions that can break it, so it covers an account switch, an app restart, a power cycle, another machine and the vendor app writing the board. Writes nothing when they already match, and at most one attempt per open. Plan: `docs/plans/fix-extended-keys-self-heal/`.
- **Extended-keys skip set** — the slots the keyboard key push and the macro resync must not write, because they hold a `{0x8x, off_lo, off_hi}` pointer into the [[Advanced-key storage area]] rather than a key record; writing one orphans the record, and for an unmanaged DKS/END loses it for good. Two independent halves, answering two different questions: `ExtendedKeySlotsInUse` (the owner's live [[Extended Keys]] rows plus the host's blocked slots — what is *claimed*), and the board's own key-matrix mirror `_assignments` (a TYPE byte in `0x80`..`0x85` — what the hardware *holds*). The second exists because the first is empty for the whole probe window and forever after a probe that failed, which let any debounced edit orphan a record nobody had read. Plan: `docs/plans/add-cyrex-extended-keys/` (round 4, M2).
- **Factory clarifications (C-numbers)** — the vendor's numbered answers (C1, C8, C12, …) to our protocol questions, recorded in `docs/knowledge-base/smart-infinite-protocol/factory-clarifications-2026-08.md`; C12 is the one stating the 2.4G receiver relays table transfers in 24-byte payloads.
- **Feature area (Smart Infinite)** — the 64-byte general-info block written with `0x15` / read with `0x14` on the [[Smart Infinite protocol]]: profile, light mode/level/speed/RGB, colour bytes, OFF/SLEEP timers, LOGO and side-light settings. Sent 56+8 over the cable. Over the 2.4G receiver the App sends it in the receiver's 24-byte relay chunks ([[Factory clarifications (C-numbers)]] C12) — QA on a live Rampage receiver saw white render cyan with the wired 56+8 shape and correct colours after the switch, though the 2026-08-13 probe had read the 56+8 write back intact; the conflict is unresolved (see `docs/knowledge-base/smart-infinite-protocol/wireless-receiver-protocol.md`).
- **Smart Infinite protocol** ("智慧无限") — vendor HID protocol of [[Cyrex]], [[Aress]] and [[Rampage]]. Report ID `0x06`, 64-byte reports (8 B header + 56 B payload), header `cmd / addr LE / len / checksum LE / status`, byte 7 = `0x55` on success. Base matrix: `0x16` read factory, `0x17` read current, `0x18` write; lighting `0x19`; device info `0x12`; config `0x14`/`0x15`; macros `0x1B`/`0x1C` (the `0x2C`/`0x2D` the V3.1 workbook lists belong to a different firmware line — see [[Macro upload (Smart Infinite)]]). Writes transfer the **full region** — key matrix 384 B (7 packets, 6 × 56 + 48); the macro region is sized by [[Macro space]] from Device Info — as bare commands: the `0x10`/`0x11` session bracket is not used for anything per the factory clarifications of 2026-08 (`docs/knowledge-base/smart-infinite-protocol/factory-clarifications-2026-08.md`); shorter transfers are acked and discarded. Reads stay data-sized. `0x20` is a factory reset — never send it. Framing in `SmartInfiniteProtocol` (Cyrex/Aress) and `RampageProtocol` (Rampage keys); RGB services still bracket their sessions (verified working, alignment pending).
- **SmartInfinite65Geometry** — the single definition of the 65% keyboard geometry shared by [[Cyrex]] and [[Aress]], keyed by [[Matrix slot]] rather than key name. Both boards are the same hardware with three navigation keys labelled differently, so each model's visual layout is the join of its own catalog against this table — keeping them in step by construction instead of by copy-paste.
- **Transport (device config)** — one connection (cable / 2.4G dongle / Bluetooth) of a device in the `AllowedDevices` catalog. A device carries its shared settings once plus a `Transports` list; each transport declares its `ConnectionType` and only the fields that differ (VID/PID, etc.), and `DeviceMapExpander` flattens device × transports into the per-transport rows the DeviceHost matches on. `HasBluetooth` is derived from `ConnectionType`; `MergeTransports` is an explicit per-device flag. `SupportsConfiguration` and `SupportsBattery` are per-transport overrides falling back to the device value — a link can be unable to configure or to report a usable charge level even when the device can (TAIPAN reports charge *voltage* over its cable, which pins at 100 % while charging, so its wired transport sets `SupportsBattery: false`).
- **Hotspot (device)** — a button-remap marker + connector line drawn over the device image; its per-device geometry (id, button/target points, label side, disabled flag) is catalog config (`AllowedDevices` → proto `DeviceHotspot`), while label text derives from the id and bindability comes from the `disabled` flag.
- **ImageScale** — optional per-device render scale (`AllowedDevices` config → catalog `image_scale`) for the details-view device image, compensating for artwork canvas padding; unset renders at 1.0.
- **DpiSwitch** — the MsConfig byte holding TAIPAN's *active* DPI stage (0–7); the physical DPI button and the app's DPI stage options both change it.
- **DPI point** — one user-editable entry of a mouse's DPI ladder: a value the user picks inside the device's range, shown as one radio option in the DPI section. Points can be added and removed within the device's slot bounds (1–8 on both BLAZE and TAIPAN, seven shipped by default), and the ladder is preset-scoped. Positional — removing one renumbers those below it, and the [[DPI step]] quantizes every value. See `docs/plans/add-custom-dpi-values/`.
- **DPI step** — the quantum a [[DPI point]]'s value snaps to, declared per device in the catalog (`AllowedDevices` → `DpiStep`, proto `dpi_step`). 50 on both mice: TAIPAN's firmware stores CPI in 50-DPI units, so one step is exactly one register increment; BLAZE stores raw CPI and its sensor's real granularity is unverified, which is why the value is configuration rather than a constant.
- **DPAPI** — Windows Data Protection API (`ProtectedData`, `DataProtectionScope.CurrentUser`): encrypts a secret with a key bound to the signed-in Windows user, so another account or a copied database file cannot read it. Used for the saved "Remember me" [[Bearer Token]], stored as `dpapi1:` + base64 in the `saved_auth.token` column; a legacy plaintext value is re-protected on first read (finding S7). Plan: `docs/plans/fix-repository-audit-findings/`.
- **Easen** — the 9-byte SetFeatureReport protocol family used by the Holtek HT68FB571 MCU (BLAZE/X43); implemented by `EasenMouseService`.
- **FlashEnable** — byte 5 of an [[RY5088]] `SET_KEYMATRIX` (`0x0A`) packet. `1` tells the firmware to persist the write to flash; `0` leaves it buffered, so the remap is lost on replug. [[T800]] sets it on every key write — one write per user action, so there is no burst of flash traffic to pace.
- **GamingKeyboard2** — the protocol command table inside [[Keyborder]] for the [[Smart Infinite protocol]] family; its numbering matches our measured Cyrex firmware (`0x17`/`0x18` matrix, `0x20` factory reset) where the V3.1 workbook did not, and it adds the magnetic-axis commands `0x36`–`0x3B`. Transcribed in `docs/knowledge-base/smart-infinite-protocol/magnetic-axis-travel.md`.
- **Guest session (`app_session`)** — the persisted 48h guest session row (plus its session-scoped `devices` list); created by "Continue as guest", removed by sign-in/sign-up via `ClearSession` or by expiry via `ClearData`. It must never coexist with a restored remember-me auth — startup drops a stale row instead of restoring it when valid `saved_auth` exists. `ClearSession` deletes only the session-scoped rows; `ClearData` is the expiry wipe that also removes guest-owned settings/macros/presets. Plan: `docs/plans/fix-remember-me-guest-session/`.
- **Guest session expiry warning** — a bell entry raised a lead time before a [[Guest session (`app_session`)]] ends, telling the guest their devices, presets, macros and settings will be deleted so they can register in time. Bell only — deliberately no in-app banner and no Windows toast — and, unlike expiry itself, not tray-gated. Raised once per session, latched by the `app_session.expiry_warning_sent` column so a restart inside the window does not re-notify. Plan: `docs/plans/add-guest-session-expiry-warning/`.
- **Guest → user migration** — the local-DB re-keying step that runs when a guest signs in or up, re-associating settings rows from the guest session UUID to the customer id.
- **Guest notification lifetime** — confirmed 2026-08-27 as intended: a guest's bell rows are deleted when the guest signs in (`ClearSession`) and when the guest session expires (`ClearData`), and follow the user **only** on guest→register, where `MigrateGuestToUserAsync` re-keys them. They are keyed by the finished session's uuid, so after sign-in no future owner could address them; pulling them into an existing account is the [[Guest → user migration]] at sign-in that was deliberately removed as a bug. Distinct from the [[Pre-owner notification flush]], which concerns entries that never had an owner at all.
- **HasNoKeyOverrideLayer** — the `DeviceDetailsViewModel.KeyAssignments` predicate for boards whose firmware has **no factory-vs-override split**: the live key matrix *is* the state, so "is this key overridden" means "does its record differ from the catalog default", and slot numbers come from the catalog rather than a runtime scancode probe. True for [[Cyrex]]/[[Aress]] and [[T800]] — two unrelated protocol families — which is why it is named for the property rather than the family; [[Smart Infinite protocol]]-only behaviour (the macro repeat encoding) still tests `IsSmartInfinite65Device`.
- **HID** — Human Interface Device; the USB device class used to talk to the mice/keyboards.
- **Configuration-mode session** — the framing every [[TAIPAN]] flash-table write is wrapped in: `0x46` Para1 `0x00` to enter (retried until acknowledged), the table write, a ONE-frame commit (ValidBankID carrying `driverPara4 = 0xD3`), `0x40 F3 <mask>` to apply, then `0x46` Para1 `0x01` to exit. The cable tolerates its absence; the 2.4G dongle does not — which is why config writes over the dongle were believed impossible until 2026-09-02. A reply carrying `driverPara4 = 0xEE` means committed. Encoded by `TaipanConfigSession`. **Nestable, and one session covers a whole apply, not each table** — entering config mode is a visible ~1 s freeze, so a per-table session made a DPI change freeze the mouse twice with a pause between. **The exit frame must be sent on every path, exceptions included: Para1 `0x00` suppresses mouse reporting, so a device left in configuration mode stops working as a mouse until replugged.**
- **Host-absent contract** — the rule that every unary RPC on [[UsbHidDeviceService]] returns its documented "no answer" value when the [[DeviceHost]] cannot be reached (false for a write, -1 for a battery level, null for a read that must not be mistaken for an empty result, an empty list for `GetDevices`) instead of throwing, and that every call carries a gRPC deadline. Pinned by `UsbHidDeviceServiceHostAbsentTests`. Losing the host is deliberately silent to the user — it is logged via `NotifyError` and nothing is shown on screen. See also [[HostAvailabilityChanged]].
- **HostAvailabilityChanged** — the [[UsbHidDeviceService]] event reporting that the [[DeviceHost]] started or stopped answering, raised on the **transition only** (the reconnect loop retries every 3 s, so a level signal would repeat forever). False means device state is no longer maintained and `HomeViewModel` marks every connected card inactive — device presence arrives only as a push, so without this the last push before the service died would stand for the rest of the session and a disconnected device kept showing as connected. True needs no payload: the host answers a fresh subscribe with the current device lists, so cards repopulate through the ordinary push path. A deliberate `StopCommunication` (tray-minimise, leaving Home) raises nothing.
- **HOGP** — HID over GATT Profile; how a Bluetooth-LE device (e.g. a [[Rampage]] on Bluetooth) surfaces its HID collections to Windows, which re-exposes them as HID devices under `BTHENUM`/`BTHLE` device paths.
- **DIS PnP ID** — the Device Information Service PnP-ID GATT characteristic; the place Windows takes a BLE HID device's VID/PID from, so a board's Bluetooth identity may differ from (or lack) its USB VID/PID.
- **Information page** — the App page opened from the "Information" item in HomeView's profile/guest dropdowns; reuses the Profile page's chrome (back-button header + chamfered dark frame) and shows three legal documents (Privacy Policy, Terms of Service, License and Sublicense Agreement) as octagon-panel tabs, each transcribed per-language (en/uk) and swapped on runtime language change. Plans: `docs/plans/add-information-page/` (shell), `docs/plans/add-information-sections/` (content).
- **InstallAcl** — `ProoveGaming.Common` helper that builds the locked-down permissions for folders an elevated process or the LocalSystem [[DeviceHost]] later trusts: inheritance from the parent disabled, Administrators and SYSTEM full control, optionally Users read-and-execute. Applied to the install folder before the payload is copied, and at creation to the payload staging folder (findings S3, S4). Plan: `docs/plans/fix-repository-audit-findings/`.
- **InstallLayout** — `ProoveGaming.Common` constants for the on-disk and registry layout the installer writes and the uninstaller reads back (EXE names, `host\` folder, service name, the HKLM uninstall key, the `--uninstall` argument), kept in one place so the two sides cannot drift (finding A2). Plan: `docs/plans/fix-repository-audit-findings/`.
- **Install pause gate (`InstallPauseGate`)** — the installer's async-awaitable TaskCompletionSource-based gate that parks the install pipeline (the UI-thread steps and the per-file copy worker) while the Cancel modal is open; replaced a blocking `ManualResetEventSlim` whose UI-thread `Wait` could freeze the installer window permanently. Plan: `docs/plans/installer-cancel-deadlock/`.
- **Install signature** — the check (`InstallSignature.IsProoveGamingInstall`) that a folder really is a Proove Gaming install before an elevated process acts on it: an acceptable location (not a drive root, system or profile folder), not a junction, and **provenance** — the folder and at least one of `ProoveGaming.App.exe`, `ProoveGaming.Uninstaller.exe` or `host\ProoveGaming.DeviceHost.exe` owned by Administrators, SYSTEM or TrustedInstaller, which a standard user cannot fake (a copy they make of one of our EXEs is owned by them), or located inside Program Files, where only administrators can write. One marker is enough on purpose, so a damaged install (AV quarantine, a half-finished uninstall) stays repairable and removable. Used by the uninstaller before deleting anything and by the installer's folder step (finding S1, review round 1 B1). Plan: `docs/plans/fix-repository-audit-findings/`.
- **Key travel area (magnetic axis)** — the flat per-key actuation table of a [[Smart Infinite protocol]] magnetic board ([[Cyrex]]/[[Aress]]): `slots × keyTravelStep` bytes read/written whole via `0x38`/`0x39`, one uint16-LE record per key (actuation point, release, RT press/release, dead zones; values in `keyStepMarker`-mm steps). Extracted from [[Keyborder]] — see `docs/knowledge-base/smart-infinite-protocol/magnetic-axis-travel.md`.
- **Keyborder** — PixelPrime's Electron driver app (`Keyborder-v3.exe`, client-supplied) for the vendor's keyboards, including PG Cyrex; its readable renderer bundle is the source of the [[GamingKeyboard2]] command table and the magnetic-axis travel protocol.
- **key_macro_bindings** — the SQLite table recording which library macro each keyboard physical key plays, keyed by owner + device + matrix slot. Needed because the on-device [[Macro library]] stores event lists only — no names or ids — so a key→macro mapping cannot be read back from the keyboard. Preset-scoped since [[preset_key_macro_bindings]]: the live row is what the device is written from, and the snapshot is what a preset switch or Discard restores it to.
- **Key matrix** — the BLAZE/X43 table (param_1 block 2) mapping each physical button slot to a 4-byte function entry; the Easen-family analogue of TAIPAN's button map.
- **Staging buffer** — the volatile RAM area a [[Smart Infinite protocol]] key write lands in. It reads back correctly but does not drive the key-scan matrix; the firmware only commits a table to the compiled profile when the **full** 384 bytes are transferred. A `Set General Info (0x15)` write clears it.

- **Device Association Service (DAS)** — the Windows service (`DeviceAssociationService`, hosted in `svchost` — "Service Host: Device Association Service" in Task Manager) that brokers device pairing/association and processes every BLE advertisement while any app scans; a long-running scan makes it accumulate per-endpoint state for every rotating random address in radio range, memory it never returns until the service restarts (see `docs/plans/fix-das-memory-growth/`). It also brokers the WinRT objects our own code asks for — `DeviceInformation` enumeration (`Bluetooth.GetPairedDevicesAsync`) and GATT session creation (`Gatt.ConnectAsync`) — so an unbounded loop over either grows it just as a long scan does. Nothing we write allocates inside it; it grows with what we *ask* of it. Measured ~8.8 GB on one tester machine and 12 GB overnight on another (2026-09-02); the predecessor 23 GB DeviceHost leak had the same shape. What does **not** move it, measured on Windows 11 26200: raw SetupAPI/CfgMgr32 enumeration (`SetupDiGetClassDevs`, `CM_Get_Device_ID_List`, `CM_Get_Device_Interface_PropertyW`) — so enumeration cadence is a CPU/wakeup concern, never the leak, and the culprit is always on the WinRT path (see `docs/audits/2026-09-02-device-association-memory-audit.md`). One further trap on that path, found when the incident recurred on 2026-09-08: `Bluetooth.GetPairedDevicesAsync` is not a listing — InTheHand resolves a **native `BluetoothLEDevice` per paired device on the machine**, ours or not, and disposes none, so every enumeration result that is not retained must be disposed (`ReleaseUnretained`) or it holds DAS state until the GC gets round to a tiny wrapper. Since that incident all four DAF paths in `BluetoothDeviceDiscoveryService` are rate-bounded by a pinned schedule — GATT connect (1 s→60 s, retire at 6), rediscovery (10 s→5 min), [[LE advertisement watcher]] reopen (0→5 min) and the sweep enumeration (30 s→5 min) — with the last two sharing one reset hook (`ResetIdleBackoff`) so a machine at rest settles into a single rhythm and any connection-state change collapses both to immediate. The lesson the recurrence taught: **a bound on how much is not a bound on how long** — the scan was already windowed, and the window was simply reopened forever.
- **DEVPKEY_Bluetooth_LastConnectedTime** — undocumented but stable Windows device property (`{2bd67d8b-8beb-48d5-87e0-6cda3428040a}`, pid 11, FILETIME) on Bluetooth device nodes: when the device was last on the link, stamped on every connect and disconnect (measured 2026-09-02); stored as local time, so read with day-scale tolerance. The signal the [[Stale ghost pairing]] veto judges by (see `docs/plans/add-stale-pairing-detection/notes.md`).
- **Stale ghost pairing** — a paired Bluetooth LE entry in Windows that can never reconnect, typically left behind because a device's BLE address changes on every re-pair (PG Taipan measured `D104…` → `D112…`): still enumerated and tracked, permanently disconnected, so it keeps the LE scan "needed" forever (see `docs/plans/add-stale-pairing-detection/`).
- **LE advertisement watcher** — the WinRT `BluetoothLEAdvertisementWatcher` that `BluetoothDeviceDiscoveryService` runs in bounded passive windows (~10 s each) while a tracked paired BLE device is disconnected, matching each advertisement's address against the tracked-device snapshot and reconnecting only on a match; the windows cap the [[Device Association Service (DAS)]] load a continuous scan used to create (see `docs/plans/fix-devicehost-ble-memory-leak/` and `docs/plans/fix-das-memory-growth/`). How often a window **reopens** is itself bounded by the **scan reopen backoff** (`ScanReopenSchedule`, 0 → 30 s → 2 min → 5 min), applied after each window that closes with no connection-state change and reset by every transition: the 10 s-per-30 s duty the windows shipped with bounded how much of the time we scan but not how long we keep doing it, and "a tracked paired device is disconnected" is the *permanent* state of a [[TAIPAN]] paired over Bluetooth but in use on its 2.4G dongle — which no scan can ever reconnect. That case took a QA machine's memory overnight a second time (`docs/audits/2026-09-08-das-dongle-incident.md`). Waiting is safe because the window is not the reconnect path: Windows reconnects HID-over-GATT peripherals itself and the [[BLE presence poll]] sees it in ~3–6 s; the window only accelerates our own GATT session. Three separate things now decide it is not needed, and they cover different cases: "disconnected" means the [[BLE presence poll]]'s tree verdict rather than `Gatt.IsConnected` (the latter reports whether *our* GATT client holds a link, so for a peripheral Windows owns it stays false and the watcher never stopped even while the device was connected); a [[Stale ghost pairing]] is vetoed out of the need entirely; and reconnection itself is bounded by a per-device backoff (1 s doubling to 60 s), after which six consecutive failures presume the instance dead and release it, since a dead InTheHand handle never reconnects and only a fresh one from the paired enumeration can recover it. Without the last of these one `Gatt.ConnectAsync` ran per advertisement indefinitely, each creating a native `GattSession` (see `docs/audits/2026-09-02-device-association-memory-audit.md`).
- **LED Param Table** — the effect enumeration in the [[Rongyuan]] YC3123 spec (`docs/knowledge-base/rongyuan-yc3123-gaming-protocol.md`) that defines `FEA_CMD_SET_LEDPARAM` (`0x07`): effect codes `0x00`–`0x19` (Off, Static, Breathe, Neon, Wave, …), `Speed` and `Bri` as **0–4** enums, and the `Option` byte as `(Type << 4) | Colour`. The [[RY5088]] doc omits all of it, which is why T800 lighting is built against this table instead.
- **LED protocol** — the byte-level protocol used to drive per-key / per-zone RGB lighting on supported devices.
- **Macro assignment (Macros page)** — binding a library macro to a physical button from the Macros page: select a [[Hotspot (device)]] on the device image, then click a macro to assign it (a `Macro` button binding, same store + device path as the Buttons page). The bound button's hotspot shows the macro name on a second line with an unassign (✕) that reverts it to the button's factory default.
- **Preset-scoped actuation** — key actuation (press/release depth and Rapid Trigger) is carried by a preset like every other section: `device_actuation` holds the live rows the UI edits, `preset_actuation` is the snapshot Save Preset copies them into, and a preset apply pushes them to the board. A preset holding **no** actuation rows writes none — that is what stops presets saved before this existed from resetting a tuned board. Values are hundredths of a millimetre, keyed by matrix slot, with slot `-1` meaning the board was written uniformly.
- **Selected-key macro badge** — *(removed 2026-08-14, `remove-macro-list-selection`)* the former floating chip on the Macros page that named the macro bound to the *selected* key, with an unassign (✕) inside it. Replaced by the key overlay's hover tooltip, which names a bound macro on mouse hover only, carries the same unassign ✕ for macro-bound keys, and works identically on the Macros and Key Assignments sections; unassigning also lives in the Key Assignment Dialog and the shared header's Reset link. The term survives in older plans' text.
- **Macro inspection (Macros page)** — the macro list's radio affordance: checking a macro (`MacroViewModel.IsInspected`) highlights every key (`IsMacroBindingHighlighted` → the overlay's `macroBound` box) or mouse hotspot its bindings point at. Pure read-only inspection — assignment lives in the Key Assignment Dialog / Buttons section — kept on flags separate from the three `IsSelected` selection models (dialog macro rows, Key-Assignments/Actuation keys, hotspots) so the surfaces cannot overwrite each other. Cleared on section leave, device switch and macro delete.
- **Macro (device-scoped)** — a recorded macro belongs to the physical device it was created on, keyed `(owner_kind, owner_id, vendor_id, product_id, device_key)` like every other per-device table, so each device shows only its own — plus the unit-agnostic `device_key = ''` shared scope the [[Sign-in pull]] writes, which `GetMacros` unions into every unit-keyed read of the same model. Databases predating this are migrated once: macros referenced by a button binding, a key binding or a preset follow that device (duplicated when more than one references them); unreferenced macros are dropped.
- **Macro library** — a keyboard's indexed set of on-device macros, uploaded as one packed blob (Raster: 1096 bytes, up to 16 macros) that key-matrix bindings point into by index. Contrast the mouse route, where a macro rides inline on its own button binding. Supported on Raster and [[T-Racer]] (one shared `RasterKeyboardMacroService`, model name passed in for logging), on [[Cyrex]] / [[Aress]] via [[Macro upload (Smart Infinite)]], and on [[T800]] via [[Macro upload (T800)]].
- **Raster family (vendor family)** — Raster and [[T-Racer]], VID `14000`: the same firmware family speaking the same `mi_01` 65/65 vendor protocol for RGB, key remap and macros. The `Raster*` type prefix denotes this family rather than the single model — `RasterMacroEncoder` also packs Cyrex/Aress libraries and `RasterKeyBounds` backs [[TRacerArtworkLayout]]. Macro upload is one shared service for both; RGB and key mapping are still a copied file each, which is how T-Racer's key mapping silently drifted and discarded macro bindings until macros were enabled for it.
- **Macro type byte (key record)** — the `TYPE` in a [[Key matrix record]] that makes a key play a [[Macro library]] entry. **It differs by family, and this byte has flipped three times — here is the per-family truth with its source, so a fourth flip requires new hardware evidence.** Raster / T-Racer: `0x60` play (`code2` = play mode) / `0x61` while-held — hardware-verified. [[Smart Infinite protocol]] boards (Cyrex/Aress/Rampage): their firmware's own `KeyType` enum (extracted from [[Keyborder]], the vendor driver that runs our Cyrex) gives `0x50` `MACRO_NO_COUNT` (`code2` = stop mode 0..3) and `0x51` `MACRO_WITH_COUNT` (`code2` = count), while **`0x60` there is FUNCTION** — a `{0x60, slot, mode}` binding is stored, verifies on read-back, and plays nothing, which is exactly how macros shipped broken on this family. The V3.1 workbook says the opposite because it describes a different firmware line. See `docs/knowledge-base/smart-infinite-protocol/macro-format-gamingkeyboard2.md`. [[T800]] ([[RY5088]]): `0x09` per the YC3123 key-code table, and the operands are **swapped** relative to both families above — code1 is the play type (0 repeat / 1 always / 2 while-held), code2 the slot; the repeat count lives in the uploaded blob, not the record.
- **Macro upload (Smart Infinite)** — shipping the [[Macro library]] to a [[Cyrex]], [[Aress]] or [[Rampage]]: the region buffer built by [[SmartInfiniteMacroEncoder]] (sized to [[Macro space]], 20-slot offset table, modifiers as hot-key events) written with `0x1C` (`sethongMessage`) and read back with `0x1B` — the commands the vendor's [[Keyborder]] app actually sends on this firmware line. The read-back verify is authoritative: a mismatch fails the upload so key slots are never bound into a library the board does not hold. The previous `0x2D` full-2048-byte transfer was acked and discarded — `0x2C`/`0x2D` belong to the V3.1 workbook's firmware line, not ours. Device Info's [[Macro space]] is checked first, and zero is refused rather than reported as stored.
- **Macro upload (T800)** — shipping the [[Macro library]] to a [[T800]]: each macro is its own per-slot blob built by [[Ry5088MacroEncoder]], written with `0x0B` in 56-byte pages (`End = 1` on the last) and read back with `0x8B` in 64-byte pages by `T800KeyboardMacroService`. All 16 App-managed slots are rewritten every upload — provided entries get content, the rest the 4-byte empty blob, so a deleted macro cannot linger. Used slots are verified by read-back (authoritative, like [[Macro upload (Smart Infinite)]]); empty-slot clears are written blind.
- **Ry5088MacroEncoder** — the pure encoder of one [[T800]] macro blob (≤256 bytes, per the YC3123 spec's "Macro Table memory information"): repeat count uint16 LE, then 2-byte `[code, attr]` words — attr bit7 = press, bits 0–6 = inline delay ≤127 ms or zero to make the next word a 16-bit delay — and a `0x00 0x00` terminator. Drops any code outside `0x04..0xEF` (0x00 is the end marker, `0xF9`/`0xFA` are motion/jump commands). Deliberately separate from both other keyboard encoders: this family stores per-slot blobs with the repeat count in the blob header, not one offset-table region.
- **SmartInfiniteMacroEncoder** — the pure encoder of the [[Smart Infinite protocol]] macro region (`formatHongRect` transcribed from [[Keyborder]]): `0xAA 0x55`, region length, 20-slot offset table, 4-byte actions with modifiers translated to the hot-key form (bitmask + attr `0x02`). Deliberately separate from Raster's hardware-verified `RasterMacroEncoder` — the two formats differ in header semantics, slot count, sizing and modifier encoding.
- **Macro slot** — one of a device's fixed on-flash macro storage areas a button binding points at (TAIPAN: 20 slots × 200 bytes, command `0x05`; BLAZE: indexed 128-byte buffers, command `0x04`).
- **Macro space** — byte 5 of the [[Smart Infinite protocol]] Device Info block, × 256: how many bytes of on-flash [[Macro library]] region the firmware has (Cyrex fw `0x0002`: 1024). The [[Macro upload (Smart Infinite)]] path reads it before writing and refuses when it is zero, so a discarded write is never reported as stored — the same guard [[Key count]] provides for key remapping. Also the size of the region buffer itself: [[SmartInfiniteMacroEncoder]] builds exactly this many bytes and the header's length field carries it.
- **merge_transports** — the `devices` column (and `DeviceCardViewModel`/`DeviceRecord` flag, from the catalog entry) marking a product that is one physical device reachable over several transports. Its routing identity changes with the live transport — [[Rampage]] enumerates as `1389/49271` plus the receiver's [[Container ID]] over the 2.4 GHz dongle and as `10473/12288` with no key over Bluetooth — so such a row is keyed by `(owner, name)` instead; stored on the row so a card restored from disk knows the rule before discovery reports in. Databases predating the column are healed once at construction, collapsing only same-name groups that hold two or more distinct `(vendor_id, product_id)` pairs (two identical units share one pair and are never collapsed). The **vendor** of such a product is now pinned too, not just the product id — see [[Settings vendor id]] and [[Transport vendor ids]]. See [[Card identity]].
- **MsConfig** — TAIPAN's 19-byte device settings block (command `0x01` write / `0x41` read) holding polling rate, active DPI stage ([[DpiSwitch]]) and profile state; changing one field requires a read-modify-write because the write erases the sector.
- **Newsletter toggle** — a proposed Profile → Account switch over `POST api/profile/notifications` / `api/profile/notifications_update`. **Built then removed (2026-08-27):** product chose not to ship it, so those two endpoints are deliberately unimplemented and the newsletter opt-in is set once at registration (`agree_newsletter`) and changed only on the website. See `docs/plans/add-newsletter-toggle/`.
- **Nickname generator** — shared Launcher API component that returns up to 5 unique nickname suggestions from an email's local part; used by `api/check_email`, `api/check_nickname`, and `api/profile/check_nickname`.
- **notifications (table)** — the SQLite table behind the Home bell: owner-scoped rows (title/subtitle stored as displayed, icon, timestamp, read flag), capped at 100 newest per owner. Written through on every add/read/delete so the history survives an app restart; guest rows die with the guest session (`ClearData`) and follow a sign-up via the guest→user migration. See `docs/plans/persist-devices-and-notifications/`.
- **Owner-change sweep** — `HomeViewModel.RestoreConnectedDevicesForNewOwner`, fired on the `CustomerId` / `IsGuest` transitions that move the settings owner (guest start, sign-in, sign-out, session restore). It re-drives the connect-time restore for everything already connected, so devices that appeared while nobody was signed in still get their owner’s state; on a genuine owner-to-owner switch it also resets lighting the incoming owner never configured (`_lastLitOwner`). It deliberately does NOT re-drive an open device page: every route to a new owner nulls `Device` first (`ClearDeviceForExit`), so a switch always arrives with the details page already closed. It also writes NO [[Pending device apply]] mark — it did between 2026-09-05 and 2026-09-12, and that silently destroyed the incoming account's applied-but-unsaved state, because the mark's consumers answer it by loading the preset snapshot over the live rows. A keyboard's configuration reaches the arriving account by [[Extended-keys self-heal]] for its records and, for remaps / macro bindings / actuation, not yet at all (named limitation of `docs/plans/fix-extended-keys-self-heal/`). Plans: `docs/plans/add-reapply-preset-on-connect/`, `docs/plans/fix-rgb-owner-isolation/`, `docs/plans/fix-account-switch-device-state/`.
- **Owner-scoped devices** — the `devices` table's two ownership modes: guest rows (`owner_kind='guest'`, rewritten whole by the session `Flush`, wiped by session expiry/sign-in) and user rows (`owner_kind='user'`, written through per change so a signed-in user's cards survive restarts). Rows carry `device_key` ([[Container ID]]) so two identical units of one model stay distinct. `HomeViewModel.ReloadOwnerScopedState` re-anchors on-screen cards when the owner changes at sign-in/sign-up; `ClearOwnerScopedState` drops the departing owner's offline cards (and bell) at sign-off so they are never adopted into the next account.
- **Owner-scoped device caches** — the in-session dictionaries on the singleton `DeviceDetailsViewModel` (`_rgbStateByDevice`, `_assertedDpiStages`, `_assertedReportRates`, `_backfilledPresets`) whose keys carry `(owner_kind, owner_id)` alongside the device's settings identity. The view model outlives every sign-in/sign-out, and a page open resolves RGB cache-first and then persists what it resolved under the current owner — so an owner-less key let one account's colours be written into another's `device_rgb` rows. `OnOwnerChanged` (called from `HomeViewModel.RestoreConnectedDevicesForNewOwner`) additionally purges other owners' entries; the owner in the key is what makes it correct, the purge only bounds memory. - **OnBeforeStorageAccess** — an internal test seam on `LocalStorageService`: a callback invoked from the single `AcquireLock()` funnel before every storage access (and before the async migration's `WaitAsync`), letting threading tests record which thread each SQLite access runs on. - **OverlayPopups** — Avalonia `Win32PlatformOptions` flag enabled in the App's `Program.cs`: popups render inside the main window instead of as separate non-activatable native windows. - **Play mode (macro)** — how a keyboard replays a bound macro, carried in `code2` of the key-matrix record: `0x00` plays through once, `0x01` repeats only while the key is held. Distinct from a repeat count, which the 3-byte record has no room for and which Raster therefore cannot express.

- **RY5088 checksum** — the `CS` byte marked in every [[RY5088]] packet layout and **defined by neither vendor document**. It is the **one's complement of the sum**, `0xFF - (sum & 0xFF)`: over bytes 0–6 stored at byte 7 for most commands, over bytes 0–7 stored at byte 8 for `SET_LEDPARAM`/`SET_SLEDPARAM`. A wrong `CS` is discarded **silently** — no ack, no error, and reads stop answering — and a plain sum is off by exactly one, which is what made two attempts at [[T800]] fail invisibly. Resolved from `docs/knowledge-base/royuan-led-encoding-notes.md` and confirmed on hardware. Like [[Smart Infinite checksum]], measured rather than trusted.
- **RY5088 key record** — one key's assignment in the [[T800 key matrix]]: **4 bytes** `[Type, Code1, Code2, Code3]`, where a plain keyboard key is `00 00 <usage> 00` and FN is `0A 01 00 00`. Two traps versus the [[Smart Infinite protocol]] form — a plain key's type is **`0x00`**, not Cyrex's `0x10`, and modifiers are ordinary HID usages `0xE0`–`0xE7` rather than a bitmask with a zero usage, so a key here is identified by its usage code alone. `Code3` is `0x00` throughout the factory table, which is what lets these ride the App's 3-byte [[Key matrix record]] unchanged.

- **Starlight vendor channel** — [[Starlight]]'s HID report `0xFD` (32 B in/out on `MI_03` `COL02`). Long recorded as dead because a bare `HidD_GetInputReport` returned 32 zero bytes in every state (2026-08-07); **corrected 2026-09-09** — it is a request/response [[CM002X1]] I2C bridge, so a read without a preceding `0x12` request reads an unpopulated buffer. Sent correctly it answers `FD 13 7A <map> <len> <data>` on all 256 sub-addresses, and a control at bogus slave addresses returns all-`0xFF` (undriven bus) while `0x7A` does not — proving a real chip acknowledges. Gives us a **response oracle** for telling "command understood" from "command ignored", which earlier LED attempts lacked. Payload bytes are unstable and carry no inferable meaning. Findings: `docs/headset/starlight/starlight-research-2026-09.md`. Probe: `starlight console`. The buffer is **consume-on-read** (one-shot). Used as an oracle on 2026-09-10, the documented CM002X1 LED commands (`0x01`/`0x03`/`0x04`) produced **no response on either framing** while `0x12` answered through the identical path (positive control passed) — so the dongle parses the I2C bridge and does not recognise the LED command set. See [[Starlight LED problem]] and `docs/headset/starlight/starlight-research-2026-09.md`.
- **Starlight LED problem** — [[Starlight]] has RGB and C-Media supplied a full [[CM002X1 LED Control Specification]], but the spec puts LED control on HID output report `0xFF` and the device does not declare it; its only vendor report is `0xFD`. **12 delivery framings** and **16 operation-mode attempts** were tried on 2026-08-07, none driving the LED. **Strengthened 2026-09-10** using the response oracle from [[Starlight vendor channel]]: commands `0x01`/`0x03`/`0x04` produce **no response** on either framing while `0x12` answers through the identical path (positive control passed), and the LED was visually confirmed unchanged — so the dongle does not recognise the LED command set, rather than the attempts merely missing. The headset's own button still cycles wave and static-colour effects, so the hardware is capable and the gap is the host-side command path. Open question: the framing for `PID_036D`, and whether it targets the dongle or must be relayed to the headset over 2.4G — indistinguishable from the host. Current vendor request: `docs/headset/starlight/starlight-vendor-request-2026-09-10.md` (the 2026-08-07 one is **superseded**; its section 1 was wrong). `SupportsRgb` stays `false` until it is settled.
- **CM002X1 LED Control Specification** — C-Media's LED protocol document (v0.3): a 16-byte HID output report on ID `0xFF` with four commands — `0x01` Start, `0x02` Stop, `0x03` Send LED Configuration (operation mode, LE colour-array size, LE update interval), `0x04` Send Color Array (LE offset + four RGB triples). - **DeviceNodeQuery** — reads Windows device **nodes** (`CM_Get_Device_ID_List` + `CM_Get_DevNode_PropertyW`), as opposed to [[DeviceContainerId]] which reads a property off a device **interface** path. Filtered to the `BTHENUM` enumerator so it touches a handful of nodes rather than the few hundred present. Also reads `DEVPKEY_Bluetooth_Battery` (`{104ea319-…}, 2`) — how Windows surfaces an HFP headset's battery when there is no GATT to read; range-guarded to 0-100 so a non-percentage reads as unknown rather than reaching the user.
- **ClassicBluetoothDeviceResolver** — pure, testable half of the above: groups `DeviceNode`s by Container ID into `ClassicBluetoothDevice` (address, Bluetooth VID/PID, name, battery). The Bluetooth identity is **not** the USB one — Cosmo is `0x05D6`/`0x000A` here and `0x0D8C`/`0x0334` over its dongle — and the catalog's Bluetooth transport matches on the former, since Windows lets users rename Bluetooth devices. Two parsing traps it exists to get right: a service node's id embeds the Bluetooth base UUID, whose final group is also twelve hex digits (`…00805f9b34fb`), so scanning for "twelve hex digits" finds the UUID rather than the address; and the vendor field's source prefix is not a fixed width (`VID&000105d6` vs `VID&02248a`), so the id is the last four hex digits, not a fixed slice. See `ClassicBluetoothDeviceResolverTests`.
- **DeviceApplyAspects** — flags saying which parts of a device's configuration an apply carries (`Led`, `Buttons`, `Settings`, `DpiStages`, `ReportRate`); anything not flagged is sent as null, the configuration frame's existing "leave this alone" — and that holds for **every** field, including the report rate, which was initially left ungated and so contradicted the rule. An apply holding `None` is skipped entirely rather than sent as an empty frame. Only the **debounced auto-apply** narrows itself — an RGB edit stages `Led` alone; preset switch, Save Preset, Discard and the connect-time restore all pass `All`, because "make the device match this state" is what those actions mean. The narrowing is a **union** across the debounce window, so an RGB tweak arriving after a button remap cannot drop the remap. Exists for a hardware reason: on [[BLAZE]] every configuration block is a flash commit, and pushing the whole state on a colour change re-committed the key matrix each time. See [[X43BlockCommitCache]].
- **X43BlockCommitCache** — per-device record of which param_1 block images [[BLAZE]] was last told to commit, letting `EasenMouseService` drop any block whose composed image is byte-identical to what the device already holds. "The caller supplied this block" and "this block differs" are different questions, and only the second is worth a flash write. Conservative by design: a block with no record yet is always kept, so the first apply of a host session commits whatever was asked for, and `Remember` records only blocks actually committed — recording one that was merely present in the payload would silently swallow the next real change to it. `Reset()` drops the whole record when the device handle is lost, because the mouse can come back re-flashed (the OEM tool and the vendor's reset both rewrite the key matrix) and a stale record would drop the write meant to restore the user's remaps; a rewrite performed while the device stays open cannot be detected at all. The apply log reports `committed=0x…`, the mask that actually reached flash. Root-caused 2026-08-17: nine "Random lighting" clicks in 34 seconds re-committed the key matrix nine times and left the mouse with left and right click dead. See `docs/mouse/blaze/key-matrix.md`, `X43BlockCommitCacheTests`.
- **Taipan battery request** — TAIPAN's battery query, sent as **`cmd 0x48` with zero parameters** — the same byte as the REPLY opcode. The vendor documents the request as `CMD_GetBATV` = `0x08`, and that value gets **no reply over the 2.4G dongle**; `0x48` gets exactly one reply per request (verified 3/3, 2026-08-07, raw=972 → 94 %). Battery is request/response — the device answers once and does not repeat without a new request. Untested over the wired cable. The generalisable lesson: on this protocol, if the documented request opcode is silent, try the reply opcode before concluding the transport is dead. See [[TaipanStateMonitor]], `docs/mouse/taipan/protocol.md`.
- **Taipan dongle config** — writing TAIPAN's configuration over the 2.4G dongle, which **does not apply** — retested 2026-08-07 driving `TelinkMouseService.SetButtonBindingsAsync` unmodified with the cable unplugged and the link proven live. The asymmetry is specific: a single-frame query ([[Taipan battery request]]) round-trips, while the multi-frame sequenced flash write (header `0xD1` → entry chunks `0xD2` → `ValidBankID` → commit `0xD3`) has no effect. The cable remains the only configuration path. Open question for the vendor: whether the radio link breaks the inter-frame sequencing the flash write needs.
- **TaipanStateMonitor** — `ProoveGaming.DeviceHost` background service that keeps TAIPAN's battery and live DPI stage current. It **requests** battery once per refresh pass ([[Taipan battery request]]) and also caches the unsolicited `0x48` (battery) / `0x49` (state) pushes the mouse volunteers on 2.4G link establishment. The request needs its own write handle — the reader opens `GENERIC_READ` only — and does not wait for the reply, because the reader loop already parses and caches it. It takes the [[DeviceGate]] for the path first: the same interface carries `TelinkMouseService`'s configuration writes, which are sequenced multi-frame flash transactions that an interleaved battery frame could land inside. **Corrected 2026-08-07:** this was previously a purely passive listener, on the belief that the dongle relayed device→host only; that is wrong for queries, though [[Taipan dongle config]] writes still do not apply. See `docs/mouse/taipan/protocol.md`.
- **Telink** — the MCU/protocol family behind TAIPAN; a 33-byte HID report (ReportID `0x05`, driverID `0xFA`) with a checksum byte, unrelated to the Easen/Holtek protocol.
- **Token rejection** — the Launcher API answering a token-bearing request with `TOKEN_REQUIRED` or `INVALID_OR_EXPIRED_TOKEN`: the server has invalidated the [[Session Token]] (30-day expiry, password change, account deletion). Detected centrally in `ApiHttpClient`, whose latched `TokenRejected` event `MainWindow` turns into one sign-out to Sign In plus a localized "session expired" notification, covering profile and sync calls alike. Plan: `docs/plans/add-global-token-expiry/`.
- **Unlit bed** — the solid-black layer drawn under the tinted backlight in [[Split artwork (base + keys)]] rendering. The vendor art's key wells were inpainted to plate colour when the baked-in backlight was stripped, which reads as "this board has no LEDs"; black makes the resting state read as *LEDs off* and gives every tint something dark to sit on.
- **Update_Para()** — the [[TAIPAN]] firmware routine a `driverPara4 = 0xD3` packet triggers, committing a sequenced flash-table write (button map, DPI table, macros). A table write is only durable once it lands: `0xD1` first packet (erases the sector) → `0xD2` continuations → ValidBankID → `0xD3` commit. Acknowledged frame-by-frame on the cable and answered with total silence over the 2.4G dongle — see `docs/mouse/taipan/taipan-button-write-reference-2026-09-01.md`.
- **Upgrade push** — the one-shot, best-effort background push `SettingsSyncService.OnGuestUpgradedAsync` starts when a guest registers a **new** account: the freshly migrated macros → presets → preferences → device state go to the account via [[SyncApiService]], so the new account's cloud state matches what the user built as a guest. Never blocks the sign-up UI (the work runs on the thread pool, observable via the internal `PushTask` seam); failures only log, a network error aborts the remainder, and `*_UID_ALREADY_EXISTS` counts as success (idempotent by uid). Plan: `docs/plans/add-api-v2-sync/`.
- **Update manifest** — the static snake_case JSON file (`version`, `download_url`, optional `release_notes`) the App polls to learn a newer build exists; served from wherever [[AppUpdateManifestUrl]] points. Anything that fails to parse — non-JSON, missing/bad `version` — is skipped silently.
- **UpdateCheckService** — App-side singleton started from `App.OnFrameworkInitializationCompleted` (deliberately not `HomeViewModel.Start/Stop`, which stop on minimise-to-tray): 30 s after startup and then every 6 h it fetches the [[Update manifest]], compares its `version` against the running assembly `<Version>`, and announces each new version once per process run via bell + in-app toast + Windows system notification. Every failure is a Debug-logged silent skip. Plan: `docs/plans/contact-us-and-update-check/`.
- **UsbHidDeviceService** — the App-side singleton gRPC client service talking to the [[DeviceHost]]; owns the [[SubscribeOnDevices stream]]'s lifecycle (subscribe, retry-every-3-s reconnect loop, deliberate stop on tray/navigation) plus the unary device RPCs and the last-known DPI/report-rate caches.
- **Vendor glow geometry (`#keys-solid`)** — the backlight shape shipped as vector paths inside the artwork itself, rather than hand-derived from it. [[T-Racer]] is the first board to have one: its `#keys-solid` group is six untransformed paths already in viewBox units, copied verbatim into `Assets/Keyboards/Glow/T-Racer.path`. The other boards' glow geometry had to be traced by hand from the stripped backlight. See [[Unlit bed]].
- **ValidBankID** — the `0x1A` marker TAIPAN requires at a table's commit offset (`0x007F`, or `0x0FFF` for macros) before a `0xD3` packet commits the write.
- **Wire speed inversion (RY5088)** — the `Speed` field of [[LED Param Table]] commands transmits inverted: a low byte is fast, a high byte is slow. Brightness is *not* inverted. The sources disagree on range — the YC3123 table says the field is `0–4`, the ROYUAN notes say the wire carries `5..1` — so we send the vendor-proven `5..1` and avoid wire `0` until hardware shows it animates rather than freezing. Not settleable by read-back: the firmware stores any speed byte unclamped (0, 6, 7 all read back unchanged), so only watching the board, or listening for the device's own `05 05 <speed>` announcement, tells them apart. Getting the direction backwards animates at the wrong rate rather than failing, so both ends are pinned by test. Note `Speed` is marked not-meaningful for **Static**, so the slider is correctly inert on that effect.
- **Xear license category** — `CmLicenseCategory` in [[CmXearSDK]]: which effect families a device is entitled to (Equalizer10Bands, AINoiseReduction, SurroundMax, HeadTracking, MCJT/Vigilance Mode, …), read per endpoint via `SupportedLicenseCategory` and unlocked per-GUID with `CmActivateLicense`. The vendor ships the GUID in a `XXXX_GUID.txt` beside the APO package (`158FD125-36BD-4A73-9E07-518869EDD288` for the CM002X1/A3 Pro family). On [[Starlight]] activation returns `CE_OK` globally, yet `SupportedLicenseCategory` stays `0` and every effect property returns `CE_LicenseError` — **unresolved whether that is missing hardware licensing or simply the missing [[APO (Audio Processing Object)]]**, since the per-endpoint reading comes from the APO itself. See `docs/headset/starlight/starlight-research-2026-09.md`.
- **X43** — a supported wired gaming mouse model; its device protocol lives under `docs/`. Sold as BLAZE.
- **Uninstall handoff marker** — the `%ProgramData%\ProoveGaming.uninstall.<sha256-of-install-path>.marker` file that stops the uninstaller's **detached self-delete loop** from eating a later reinstall. The uninstaller cannot delete its own EXE while running, so it leaves a PowerShell (or `cmd`) loop retrying the folder delete for ~2 minutes; that loop deletes a *path* and cannot tell the old install from a new one, so a quick uninstall-then-reinstall used to get partially deleted (files missing, app dying on `libSkiaSharp`). The loop now runs only while the marker exists, and the installer kills the pid named in it and removes it before copying. Kept **outside** the install folder so the loop cannot delete its own marker mid-cleanup, and out of `%TEMP%` because that is profile-relative while the two sides elevate independently. The kill is guarded by `ShouldStopSelfDeleteProcess` (marker age, process name, start time bounded both sides) so a stale marker whose id Windows has recycled cannot make the elevated installer kill an unrelated shell. `ProoveGaming.Common/Classes/UninstallHandoff.cs`; diagnosis in `docs/support/missing-files-crash-analysis.md`.
- **Reboot-scheduled deletion (`PendingFileRenameOperations`)** — the machine-wide `REG_MULTI_SZ` under `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager` that Session Manager acts on during the next boot; `MoveFileEx(MOVEFILE_DELAY_UNTIL_REBOOT)` writes to it. It condemns a **path, not a file**, so a path scheduled and then successfully deleted stays condemned and the next boot deletes whatever occupies it. Only files that survived the uninstaller's delete passes were ever scheduled — in practice always the same four, because the uninstaller runs from the install folder and loads the App's `libSkiaSharp.dll` / `libHarfBuzzSharp.dll` / `av_libglesv2.dll` from it. **We no longer use it** — the fallback was removed on 2026-09-15 after those four condemnations destroyed a fresh install. The installer still *clears* entries under its install folder, for uninstaller builds already in the field. See `docs/support/missing-files-crash-analysis.md` (cause 3) and [[Uninstall handoff marker]].
- **Xear** — C-Media's audio-effects technology stack (driver/APO). Enabled only when its software authenticates against a [[CM002X1]] coprocessor over HID report `0xFD`; it is a licensing gate, not a device-control channel, and Proove Gaming does not use it.
