The problem in one paragraph

On Cyrex, command 0x2D (设定宏信息) acknowledges every packet with 0x55 — at every transfer shape, including the full 2048-byte MACRO_TAB from your C8 answer — and 0x2C reads the entire 2048-byte region back as zeros after every attempt. On Rampage (RM1), 0x2C/0x2D return status 0x0F on every packet, with and without a preceding 0x10. Key remapping works on both boards using exactly the rules you gave us, so the transport is proven correct — the macro subsystem specifically does not store.

04 Rampage (RM1) fw 0x0100 — 0x2C/0x2D rejected with 0x0F, session or not

On the same firmware where bare 0x18 key writes work (your RM1 answer, confirmed), the macro commands are not reachable at all:

A  bare 0x2C read:      status 0x0F
B  bare 0x2D write:     status 0x0F
C1 bracketed 0x2D 2048: acked=0 rejected=37 (every status 0x0F) silent=0
C2 in-session 0x2C:     every read status 0x0F

Your documentation describes 0x0F as the session-lapse status — but here it is returned on the very first command immediately after 0x10 was sent and acknowledged, so that reading cannot apply. This firmware uses the older command numbering (key matrix on 0x17/0x18, not 0x1A/0x1B), and the macro command bytes for it have never been documented to us.

05 Ruled out

  • Transport / framing / checksum / interface — proven by working key writes on the same handle, same additive checksum, both boards.
  • Transfer length — 30 bytes, the 1024 boundary and the full 2048 all behave identically on Cyrex.
  • Session bracket — with and without, identically.
  • Wrong read offset — the read-back scans the entire 2048-byte region, not just offset 0.
  • Packet pacing — the same 4–5 ms pacing the working key writes use.
