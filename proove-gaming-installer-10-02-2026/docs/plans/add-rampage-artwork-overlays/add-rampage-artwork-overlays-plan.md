# Rampage artwork key overlays — implementation plan

Sibling work: [`rampage-key-assignments`](../rampage-key-assignments/rampage-key-assignments-plan.md)
(the remap feature this polishes), [`add-tracer-artwork`](../add-tracer-artwork/add-tracer-artwork-plan.md)
and [`add-cyrex-aress-parity`](../add-cyrex-aress-parity/add-cyrex-aress-parity-plan.md) (the two
prior boards that got measured artwork overlays; this plan is the same recipe applied to Rampage).

## Goal

The Key Assignments / Macros overlay for **Rampage** currently renders as the bare-canvas fallback:
abstract unit-grid buttons with text labels on an empty background. Every other interactive board
(Raster, T-Racer, Cyrex, and Aress via Cyrex's artwork) draws its clickable key overlays directly
on the rendered keyboard artwork, registered to the real keycaps. Make Rampage look and behave the
same: overlays drawn on `PG_Rampage_base.svg` + `PG_Rampage_keys.svg` (with legends), using keycap
bounds measured from the artwork itself.

## Scope

**In scope**

- A measured per-keycap bounds table for the Rampage artwork (`RampageArtworkLayout`), generated by
  a script kept next to this plan — never hand-authored.
- The one dispatch branch in `DeviceDetailsViewModel.ArtworkKeyOverlayLayout` that routes Rampage
  onto the artwork-overlay path.
- Tests mirroring the existing artwork-overlay gate tests.

**Out of scope**

- Any change to the remap/write path — `rampage-key-assignments` owns that and it is
  hardware-verified; this plan is presentation only.
- Any change to the artwork assets themselves (base/keys SVG, glow, legend paths all exist and are
  already rendered by the RGB preview).
- The bare-canvas fallback path — it stays intact for future boards without a measured table.
- Aress/Cyrex/Raster/T-Racer — no behavior change; their tables and dispatch are untouched.

## Options considered

### Option A — measure the artwork, generate `RampageArtworkLayout` keyed by key name *(recommended)*

Same recipe as T-Racer and Cyrex: decode the keycap layer's embedded PNG
(`PG_Rampage_keys.svg` carries one `<image>` 1420×487 placed by
`translate(35.936 49.482) scale(.984)`), connected-component-label its alpha channel, map each
component's bounds into viewBox space (0 0 1471.412 577.563) via that placement transform, assign
components to `RampageKeyCatalog` entries, and emit a static C# table keyed by `DevKeyName` — the
same shape as `TRacerArtworkLayout`.

*Trade-off:* the table is tied to this artwork revision; replacing the keys SVG silently
invalidates it. That is the accepted, documented property of all three existing tables, guarded by
a catalog-coverage test.

### Option B — scale the existing `RampageVisualLayout` grid onto the artwork

Draw the art layer and place the existing 34px-unit grid over it with a fitted scale/offset.

*Rejected.* This is exactly the drift the artwork tables were introduced to eliminate: the
idealised grid's proportions differ from the rendered board (T-Racer's plan measured the
mismatch), so overlays would sit visibly off the keycaps — worse than the current bare canvas,
because misregistration on a rendered board reads as a bug while the abstract canvas reads as a
stylistic choice.

### Option C — key the table by matrix slot, like `CyrexArtworkLayout`

*Rejected as unnecessary.* Cyrex is slot-keyed only because Aress borrows its artwork and joins
its own catalog by slot. Rampage's artwork depicts Rampage and no other board borrows it;
`DevKeyName`-keyed (the Raster/T-Racer shape) is simpler and matches how the code-behind consumes
bounds (`ArtworkKeyBounds[key.DevKeyName]`).

## Recommended approach

**Option A.** Concretely:

1. **`measure-rampage-artwork.py`** (in this plan's folder, run from the repo root) — sibling of
   `docs/plans/add-tracer-artwork/split-tracer-artwork.py`, deliberately as strict: it aborts on
   anything unexpected rather than emitting plausible-but-wrong numbers.
   - Parse `src/ProoveGaming.App/Assets/Keyboards/PG_Rampage_keys.svg`, decode the embedded PNG,
     read its alpha channel.
   - Connected-component labelling with the established constants (`ALPHA_THRESHOLD = 128`, a
     minimum-area filter for antialiasing specks).
   - **Hard gate:** expect exactly **87** components — the 86 remappable keys plus FN. Any other
     count aborts the script with a diff against expectations (the Aress precedent: an artwork
     that does not depict its own board must be detected here, not shipped).
   - Group components into rows (y-clustering), sort each row by x, and walk them against
     `RampageKeyCatalog.Keys` in the catalog's own order (the catalog is ordered by firmware slot,
     which is visual scan order top-left → bottom-right), inserting FN at its known bottom-row
     position. Cross-check each assignment by nearest-relative-position against
     `RampageVisualLayout` and abort if any residual is implausible.
   - Map bounds into viewBox units via `translate(35.936 49.482) scale(.984)` (read from the SVG,
     not hardcoded).
   - Emit `src/ProoveGaming.App/Models/Keyboards/RampageArtworkLayout.cs` in the exact shape of
     `TRacerArtworkLayout` (ViewBox constants + `IReadOnlyDictionary<string, RasterKeyBounds>`),
     with FN deliberately absent, and a remarks block naming this script as the generator.
2. **Dispatch** — in `DeviceDetailsViewModel.ArtworkKeyOverlayLayout`, add the Rampage branch
   (keyed by name, next to the T-Racer branch). `KeyOverlayArt` already resolves to Rampage's own
   `RgbKeyboardArt` for Rampage, and `RasterKeyboardOverlayView` already renders the art layer,
   sizes the stage from the viewBox and skips keys without bounds (FN) — no view or code-behind
   change is needed.
3. Nothing else moves: `RampageVisualLayout` stays as the fallback data source for
   `PhysicalKeys` construction and canvas sizing (`OverlayCanvasWidth/Height` are still consumed
   when `UseArtworkKeyOverlays` is false, and existing tests assert them).

## Acceptance criteria

1. Given a Rampage is connected (wired or Bluetooth — rendering is identity-by-name), when the
   user opens Device details → Key assignments, then the on-screen keyboard is the rendered
   Rampage board (chassis, keycaps, legends) with clickable overlays sitting on the keycaps — not
   the abstract grid with text labels.
2. Given the overlay is shown, then exactly 86 keys are clickable, FN has no overlay, and no
   overlay is visibly offset from its keycap at any window size (the stage scales uniformly).
3. Given the Macros section is opened on a Rampage (if macros are ever enabled for it) or Key
   assignments is reopened after switching devices, then the same artwork rendering is used —
   both sections share one overlay view.
4. Given a Raster, T-Racer, Cyrex or Aress board, when Key assignments is opened, then its overlay
   renders exactly as before this change (their tables and dispatch order are untouched).
5. Given a hypothetical board with artwork but no measured table, then the bare-canvas fallback
   still works (the `ArtworkKeyOverlayLayout == null` path is preserved and covered by the
   existing tests).
6. Given the generated table, then every bounds rectangle lies fully inside the viewBox
   (0 0 1471.412 577.563) and every `RampageKeyCatalog.DevKeyName` is present — verified by an
   automated test, so a stale or partial regeneration fails CI-local runs rather than shipping.
7. `dotnet build ./src/ProveGaming.slnx` and `dotnet test ./src/ProveGaming.slnx` pass.

## Test strategy

This is an `add-*` change; the tests below are required coverage.

### `tests/ProoveGaming.App.Tests`

Extend **`ArtworkKeyOverlayGateTests.cs`** (mirroring its existing per-board facts):

- Rampage device → `UseArtworkKeyOverlays` is true; `ArtworkViewBoxWidth/Height` equal
  `RampageArtworkLayout.ViewBoxWidth/Height`.
- Every `RampageKeyCatalog.Keys` entry's `DevKeyName` is a key in `vm.ArtworkKeyBounds` (the
  coverage guard that catches a stale regeneration or a renamed catalog entry).
- No table entry is orphaned: every `RampageArtworkLayout.Layout` key exists in the catalog
  (FN is absent from both, so this holds symmetrically).
- Every bounds entry lies within the viewBox and has positive width/height.
- Raster/Cyrex/Aress gate facts stay green (regression guard for acceptance criterion 4).

### Deliberately not automated

- **Pixel-level alignment of overlays to keycaps.** Needs eyes on a rendered visual tree; the
  measurement script's residual check and the QA checklist cover it.
- **The measurement script itself.** It is dev-tooling that runs once per artwork revision; its
  hard gates (87 components, residual bound) are its own tests.

## QA (manual test steps)

1. Launch the Proove Gaming app with a Rampage keyboard connected. Open the Rampage device card →
   **Key assignments**.
   *Expected:* you see the actual rendered Rampage keyboard (dark chassis, keycaps with printed
   legends) and the keys highlight when you hover/click them — the same look Cyrex and Aress have.
   There is no plain grey grid of labelled rectangles.
2. Click **Esc**, then **Right Arrow** (bottom-right corner), then **Space**, then **Left Shift**.
   *Expected:* each click highlights the box exactly on that keycap — no highlight lands on a
   neighbouring key, and the highlight box hugs the keycap edges.
3. Look at the **FN** key (bottom row, right of the space bar area).
   *Expected:* it is drawn as part of the keyboard picture but is **not** clickable and never
   highlights — FN cannot be remapped.
4. Resize the app window smaller and larger.
   *Expected:* the keyboard picture scales smoothly and the highlight boxes stay glued to their
   keycaps at every size.
5. Remap one key (e.g. E → A), press the physical key to confirm, then remap it back.
   *Expected:* remapping works exactly as before this change — this feature only changed the
   picture, not the remapping.
6. Connect a **Cyrex** or **Aress** (and, if available, a **Raster** or **T-Racer**) and open Key
   assignments on it.
   *Expected:* those keyboards look and behave exactly as they did before.

## Review focus

- `null-safety` — the new dispatch branch must keep the `ArtworkKeyOverlayLayout == null` fallback
  intact for boards without tables; no `!` on the layout lookup.
- `UI-thread affinity` — the table is a static readonly dictionary; nothing may compute or decode
  artwork at render time. The overlay rebuild path must stay allocation-light as it is today.

## Performance & quality

- **Hot paths:** none. The table is a static dictionary built once; the overlay is rebuilt only on
  `PhysicalKeys.CollectionChanged` (device change), exactly as today. No per-frame work, no I/O.
- **Allocations:** one dictionary at type-init; per-rebuild allocations unchanged from the
  existing artwork boards.
- **Thread-safety:** static immutable data; no shared mutable state introduced.
- **Resource lifetime:** no new disposables, no new subscriptions (the view's existing
  subscription bookkeeping is untouched).

## Risks

1. **The Rampage artwork may not depict the Rampage board** — the Aress precedent (its artwork
   drew 16 top-row keys against the board's 15, making measurement impossible). *Mitigation:* the
   script's hard gate — exactly 87 alpha components, each assignable to a catalog entry within a
   tight positional residual against `RampageVisualLayout`, abort otherwise. If the gate fails,
   the fallback options are (a) keep the bare canvas, or (b) a Cyrex-style borrow if some other
   board's artwork matches; either comes back to the user as a decision, not a silent choice.
2. **Table tied to the artwork revision.** Replacing `PG_Rampage_keys.svg` silently invalidates
   the measured bounds; nothing detects the mismatch automatically. *Mitigation:* the same
   documented contract the other three tables carry — regenerate via the script; the
   catalog-coverage test catches renames/removals but not pure position drift.
3. **Legend duplication.** Over artwork, overlay buttons carry no text (the SVG legends show
   through); if the Rampage legends were stripped into `Legend/Rampage.path` and the keys layer
   ships without them, the unlit board must still show legible legends via the legend layer —
   verify in QA step 1 that key letters are visible. (The RGB preview already renders this
   correctly, so the risk is low.)

## Open questions

- none — the artwork, glow and legend assets all exist and the rendering pipeline is already
  shared; this plan is measurement + one dispatch branch.
