Engineering status report

Rampage key assignments

29 July 2026 PG Rampage · VID 0x28E9 · PID 0x3258 features/Rampage-newkeysdoc

Update — 4 August 2026: factory answered (RM1), fix confirmed on hardware

Commands 0x10/0x11 must not be used at all, only 0x18 is sent, and the transfer must total exactly 384 bytes (7 packets: 6 × 56 + 48). No previous attempt had ever sent that exact shape — the "392-byte" variant silently dropped its 7th packet. The write path was updated and re-tested on the physical keyboard: slot 33 Q → W verified on read-back and the physical key emitted w immediately — no replug, no commit command. Key remapping on Rampage works. The report below describes the state before this update and is kept for the record.

Bottom line

Key remapping is blocked by the keyboard's firmware, not by our software. The device reports that it has zero remappable keys and silently discards every key-table write — while accepting and permanently storing configuration writes sent over the same connection in the same way.

That contrast is what proves our implementation is correct. The work is complete and tested; it cannot function until the vendor confirms whether key remapping is enabled in this firmware build.

02 What we did this round

New vendor material arrived: the factory key table, the key-type catalog, and six protocol capture screenshots. We rebuilt the protocol layer from the captures rather than the written documentation — and found four real errors in the latter.

CorrectionDocumentation saidHardware shows
Command direction0x17 = write, 0x18 = FN layer0x17 = read, 0x18 = write
ChecksumCRC16/ModbusAdditive sum, verified against 12+ captured packets
Transfer size7 packets / 384 bytes6 packets / 336 bytes
Interface selectionGuess by report sizeusage 0x20 / page 0xFF87

We also fixed a defect of our own: the read matched replies by arrival order, but every reply on this protocol arrives one command behind. Replies are now matched by the address they echo back, which is self-correcting.

Delivered: protocol layer, 86-key catalog derived from the vendor's factory table, on-screen keyboard layout, service contract, device-host handler, and app UI. 434 automated tests pass.

03 What we were trying to do

The vendor's own documented procedure, which we followed exactly:

  1. Read the current key table from the keyboard (0x17, six packets)
  2. Change the three bytes belonging to the key being remapped
  3. Send the entire table back (0x18, six packets)
  4. Read it back to confirm

Every other field decodes correctly, so the block is being read and interpreted correctly. The device simply declares that it has no keys available for remapping — while returning a complete, valid 96-key table when asked for one.

Measurement B — writes work, but only non-table writes

After sending a lighting configuration command with known values, reading the configuration block returns them byte for byte:

Configuration block (0x14)

00 0A 3B 03 00 00 76 20 EE 07 …
   10  59   3        118  32  238

   mode 10 · brightness 59 · speed 3 · RGB(118, 32, 238)   — exactly what we sent
Write typeCommandAcknowledgedPersists

This is the decisive control. A successful write round trip over the same connection, in the same session style, with the same checksum, proves our transport, checksum, framing, interface selection and read path are all correct. Nothing on our side is at fault.

Conclusion

The device accepts configuration writes, rejects table writes, and reports zero remappable keys. The straightforward reading is that key remapping is not enabled in this firmware build. The 96-key table we can read is the factory default compiled into the firmware; the feature that would let it be changed appears to be switched off.

06 What we need from the customer

In priority order. Any one of the first three unblocks the feature.

#RequestWhy it unblocks
1 Confirm whether key remapping is enabled in our firmware build. Device Info byte 6 (key count) reads 0 — should it be 96? If not, which firmware version enables it, and can existing units be updated? Directly explains both measurements
2 A USB packet capture of the vendor's own configuration tool performing one key remap — both directions, timestamped, from clicking Apply until the key changes A single trace answers every remaining question at once
3 The vendor configuration tool itself We capture the traffic ourselves; costs the vendor no engineering time
4 Why does the configuration write persist while the two table writes are acknowledged and discarded? Are table writes gated on the key count, or on a separate write-enable? Would confirm or refute the diagnosis
5 Is there a status or error code for a rejected write? Every packet returns success regardless A discarded write is currently indistinguishable from an accepted one
6 The documentation says a full 384 bytes must be sent; the vendor's own capture shows 336. Which is correct? Removes a contradiction in the source material

Cheap check on our side first: if a second Rampage unit is available, reading its Device Info tells us whether the zero key count is specific to this sample — a firmware or reflash issue — or common to the batch, a build issue. That is a two-minute test and worth doing before the vendor is contacted.
